# Security policy

## Supported versions

Only the latest release receives security fixes. Upgrade before reporting an issue you found on an older version.

## Reporting a vulnerability

Report vulnerabilities privately through GitHub: open the [Security tab](https://github.com/michael-palmes/offsider/security) of this repository and choose **Report a vulnerability**. Please do not open a public issue.

Include the Offsider version (`offsider --version`), your macOS and Xcode versions, and steps to reproduce. You will get an acknowledgement as soon as practical, and a fix or mitigation plan once the report is confirmed.

## Scope and threat model

Offsider is a local command-line tool that AI agents and scripts run on a developer's Mac to read and drive simulators, emulators and USB devices. This file lists everything it touches and the controls around each, as of the hardening that followed an external security review.

It is built for these risks:

- **An agent that follows the wrong instructions.** Text on a device's screen, in a web view, a notification or a log is written by the app under test or by whoever can put text in it. Offsider treats it as data: it escapes and caps what it prints, and the bundled skill tells agents to stop and ask when screen text asks for anything.
- **An agent that reaches too far.** Physical devices, saved secrets, linked apps, unlock codes and loosened settings each need a person at the Mac, in a terminal, confirmed with Touch ID or the login password. No environment variable or flag bypasses that: the iPhone runner's team is the one the person chose, and building it under a new bundle prefix or registering a device needs that person too.
- **Secrets in output.** Password values never print, screenshots mask password fields by default, logs are redacted, and typed text never appears in Offsider's output, errors or arguments. The iPhone runner's log and XCTest's result bundles, which XCTest writes, have not been checked for typed text; Offsider deletes both when the session stops.
- **Other local users and planted files.** Every file and socket Offsider keeps is private to the user, opened without following symlinks and checked before use.
- **A tampered install or release.** Releases are built without secrets, signed in a separate job, run with library validation on, and check their bundled files against digests compiled into the binary.

Out of scope: a hostile process already running as the same user can read the user's files and Keychain items it is allowed to read, and drive any device itself; Offsider's controls make its own path harder, not that one. Where a control only raises the bar against such a process, this file says so.

## Network

Offsider has no telemetry, no accounts and no update checks. It never connects to non-loopback addresses, never resolves hostnames and never sends telemetry. It uses Unix sockets and loopback TCP to local developer daemons only: the adb server, the Android Emulator's gRPC endpoint, usbmuxd and Metro.

- Metro: `rn open` reads `/status` on 127.0.0.1 at the port passed to it, one HTTP request with a 2 s timeout, no proxy, and never follows a redirect (a 3xx reads as "something else answered").
- adb: over loopback TCP (127.0.0.1, ::1) or a Unix socket; `ADB_SERVER_SOCKET` pointing anywhere else is refused, and a `localfilesystem:` socket whose server runs as another user is refused (`getpeereid`). Offsider starts the SDK's own adb with mDNS off (`ADB_MDNS=0`) when none is running, and that server keeps running afterwards like any adb server. A shell or exec command that prints more than 64 MB is stopped.
- `xcodebuild`, which builds the iPhone runner, talks to Apple's developer services for provisioning, as Xcode does; Offsider passes it only the proxy variables for that.

## On the Mac

Offsider keeps its state in a private per-user directory, `offsider-<uid>/` under the per-user temp directory from `confstr(_CS_DARWIN_USER_TEMP_DIR)`, which ignores `TMPDIR` (falling back to `$TMPDIR/offsider-<uid>/` when it cannot be used). It is mode 0700, owned by the user and checked on every use. Every file in it is 0600, written to a fresh file and renamed into place or created exclusively, and read only when it is a regular file owned by the user, opened without following symlinks and without blocking, so a FIFO planted in its place is refused rather than hanging a command.

- `locks/`: one file per device driven, holding only the holding command's pid, name and start time. The lock is advisory and never inherited by the processes Offsider starts. While `record-video` runs, a `<device>.recording` marker beside it makes `login` refuse to type.
- `trees/`: the last accessibility tree read from each device, named by the first 16 hex digits of a SHA-256 of the platform and device ID, so device names never reach a file name. It holds the tree as `describe-ui` prints it without the `native` attributes (no process IDs or class names), with password values, revealed password fields and the values of the evidence run's and `offsider.mask.json`'s ids and email masks already hidden, plus the writing command, timestamps, the screen's size, rotation, display and posture, and a boot marker. It is capped at 1 MB, ignored from an earlier boot of the device, and deleted once 10 minutes old by the next command that reads or writes the cache, whichever device it belongs to. Beside it, `<hash>.secure.json` records the id and frame of up to 32 password fields, so a field a show-password toggle turned into plain text is still hidden; it is swept with the tree. It serves `describe-ui --diff`, verify change lists and the tap guard, and is never sent anywhere. `OFFSIDER_TREE_CACHE=off` turns it off.
- `leases/`, `runs/`, `signins/`, `orientation/`, `displays/` and `unlock/`: lease records, evidence run records, sign-in records, Android auto-rotate records, foldable phone panels and failed unlock code markers, as [docs/privacy.md](docs/privacy.md#what-offsider-keeps-on-your-mac) describes. None holds a username, password, code or screen text.
- `logs/`: the emulator's output from `boot`, `boot-<avd>.log` (the AVD name made safe for a file name), emptied once it passes 5 MB.
- `ios-devices/<UDID>/` and `sessions/`: iPhone and iPad runner and broker records and logs, each Android device's warm helper socket and log, `android-<hash>.sock` and `.log`, named by a hash of the serial, and each simulator input broker's log, `simulator-<hash>.log`, named by a hash of the UDID (below).
- The HID broker's per-user Unix socket under `$TMPDIR/offsider-hid-<uid>` (below).

Outside it:

- `~/.config/offsider/allowed-devices.json`, the allow-list of physical devices (below). The folder is 0700 and the file 0600, written atomically under a lock, read with a 64 KiB cap. Its path comes from the password database (`getpwuid_r`), never `HOME` or `XDG_CONFIG_HOME`; a `~/.config` symlink is followed once, and only to a folder the user owns that others cannot write.
- The login Keychain: saved test users, unlock codes and the allow-list's seal (below).
- `~/Library/Caches/offsider/runner/`: the iPhone runner's build (below).
- Files you ask for. Screenshots, diffs and recordings are written 0600 to `--output` or to a generated name in the current directory. A generated name never replaces a file (a taken name gets ` 2`, ` 3` and so on), and the device name in it loses separators, control, bidi and zero-width characters. `--output` naming an existing file replaces it whole, through a sibling temporary file, `fsync` and rename, only when it is a regular image or video file the user owns; a link, a directory or another kind of file is refused, and nothing is deleted first. `record-video` writes into a private 0700 staging folder beside the target.
- Evidence run folders, after `offsider run start <dir>`: created 0700 with a `.gitignore` of `*`, holding `run.json`, `manifest.ndjson`, a lock file and the captures, each 0600. A run whose recorded folder is no longer a real directory the user owns that others cannot write, holding that run's `run.json`, is refused (`run_unavailable`).
- `type --file` and `batch --file` read one regular UTF-8 file of at most 64 KiB, judged after symlinks resolve, opened without blocking (a FIFO is refused) and checked to be the file that was resolved. Files under `~/.ssh`, `~/.aws`, `~/.config`, `~/.gnupg`, `~/.docker`, `~/.kube`, `~/Library/Keychains`, `~/Library/Application Support/offsider` and `/etc`, and names such as `.env`, `.env.*` (not `.env.example`), `.netrc`, `.git-credentials`, `.npmrc`, `.pypirc`, `id_*`, `*.pem`, `*.p12` and `*.key`, and `~/.android/adbkey`, shell history files, `*.jks`, `*.keystore`, `credentials*.json` and `*.tfstate`, are refused. `--allow-path` lifts that only after a person confirms the resolved path with Touch ID or the login password at a terminal (`person_required` without one), and only while the name still resolves to that path; a batch's `type --file` step reads such a file only when `batch --allow-path` confirmed it. Every read prints the resolved path and size to stderr.
- `offsider init` writes its skill to `~/.claude/skills/offsider`, `~/.agents/skills/offsider` or the directory you pass with `--dest`. For an agent whose folder already exists it also merges permission rules into `~/.claude/settings.json` (only `permissions.deny` and `permissions.ask` gain entries; other keys keep their values) or writes `~/.codex/rules/offsider.rules`, through a 0600 temporary file and a rename, reading at most 1 MiB and leaving a malformed file as it is. It never creates either agent's folder.
- `offsider.mask.json` and `offsider.login.json` are read from the working directory up to the repository root, at most once per command, capped (64 KiB for the mask file), as regular files, following a symlink only inside the folder.
- Files other programs write that Offsider reads, such as the emulator's discovery and `.ini` files, its boot log and the evidence manifest, are opened without following symlinks and without blocking, must be regular files and are capped (1 MiB, 16 MiB for the manifest), so a FIFO or `/dev/zero` planted there reads as no file. A unit test fails on a new plain Foundation file read in the sources outside a short, justified list.

Processes Offsider starts get an allow-listed environment, never the caller's whole one: a base set (`HOME`, `PATH`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_*`, `__CF_USER_TEXT_ENCODING`) plus, per kind of child, `DEVELOPER_DIR` for short-lived Apple tools (`simctl`, `devicectl`, `open`), the Android SDK and AVD locations for the emulator (with `ADB_MDNS=0`, and `ANDROID_EMU_ENABLE_CRASH_REPORTING=0`, though the emulator does not document that variable, so its effect is unconfirmed), the SDK, key and socket settings for `adb start-server` and other adb calls (with `ADB_MDNS=0`, never `ADB_TRACE`), `DEVELOPER_DIR` and `OFFSIDER_*` for Offsider's own iPhone and simulator brokers, the SDK, key and adb server settings and `OFFSIDER_*` for its Android brokers (with `ADB_MDNS=0`), and `DEVELOPER_DIR`, `TEST_RUNNER_*` and the proxy variables for `xcodebuild`. Detached children start in their own session with `POSIX_SPAWN_CLOEXEC_DEFAULT`, so they inherit no file descriptor but stdin (`/dev/null`), stdout and stderr; their logs are opened by Offsider without following symlinks, and must be regular, owned by the user and single-linked. The sockets Offsider opens or accepts itself (its brokers' listeners and connections, adb, usbmuxd, the iPhone runner and the screen stream) are close-on-exec as well, so a child that a library starts some other way does not inherit them. The emulator gRPC connection is not among them: Network.framework opens it. Every broker (simulator input, Android helper and iPhone session) turns off core dumps (soft and hard limit 0) and keep at most 256 open files before they open any device or socket, so no core file can hold frames, tokens or typed text.

Every coordinate, delta and distance a command takes must be finite and within -100,000 to 100,000, and a display a device reports must be at most 16,384 pixels a side. Every decoder for device and daemon bytes (adb's shell and sync packets, the helper's frames, usbmux and the session broker) refuses a length over its cap at the header, before buffering anything.

`doctor` lists your other running `offsider` processes by reading each one's arguments and keeps only the subcommand and the `--device` value: never typed text, other arguments or other environment variables.

## What reaches your agent

Whatever Offsider prints reaches your agent, and from there whatever it sends to its model provider. Offsider itself sends nothing.

- **The screen, as text.** `describe-ui`, selectors, `wait`, `assert`, `--verify` change lists and errors carry the screen's labels, values, ids and window titles. Password values read as bullets, one per character. Control (C0, DEL, C1), bidi, zero-width, soft hyphen, line and paragraph separator, interlinear annotation, tag and variation-selector characters in any of that text print as JSON-style escapes such as `\u001b`, so an OSC 52 clipboard write, hidden tag text or a payload smuggled in variation selectors shows inert (a lone U+FE0E or U+FE0F after a visible character, as every emoji label carries, stays as it is). A window title holding one is quoted, and screen text inside an error sentence is JSON-quoted, so a label cannot close the quote and finish the sentence. Each tree string (label, value, id, title) is cut at 500 characters or 500 scalars (`…(+N)`), so a flood of combining marks cannot stretch one character; an `Error:` or `Try:` line, and a JSON error's `message` and `hint`, stop at 4,096 characters. An `Error:` line's continuation is indented, so screen text cannot start a line of its own. The `Try:` line holds only the error's `hint`, escaped the same way, and a hint never holds typed text, a password or an unlock code. JSON escapes the same characters (with `list-devices --json`, `doctor --json` and `describe-ui --raw-source` too) and still decodes to the original. A tree is cut at 64 levels or 50,000 elements, with a note.
- **Values in the tree.** `describe-ui`, `--verify` change lists and `wait` and `assert` output replace one-time codes after a keyword, card numbers, wallet addresses and recovery phrases in labels and values (never ids) with `[redacted ...]` markers, and count them; `--has-value` still compares the real text. A plain field at the id or frame where the cache last saw a password field (a show-password toggle) reads as bullets and counts as `revealed`; without the tree cache there is no record and no such check. `offsider.mask.json` hides more by id, label, label text, value pattern or email, in trees, the cache, `--verify` lists and screenshots. Redaction works by pattern, so a secret in another shape still shows.
- **The screen, as pixels.** Screenshots mask password fields by default, after one tree read, plus whatever `offsider.mask.json` names; a field without a frame withholds the image. Masks cover only what the accessibility tree describes: web views, canvases, images, a secret in an ordinary text field (a show-password toggle, a custom PIN pad) and anything drawn between the tree read and the capture can still show. Evidence runs also mask email addresses. Video is never masked by the tree: `record-video` and `stream-video` check once, before the first frame, that no password field and nothing `offsider.mask.json` names is on screen, so one that appears later is recorded.
- **Logs.** `logs` redacts by key (passwords, tokens, keys, cookies, `Authorization`, JWTs, emails, seeds and recovery phrases, private keys, one-time and verification codes, bank, card and identity numbers, wallet addresses), masking a key's whole value when it is an array or object, and by value pattern (wallet addresses, Luhn-valid card numbers, 12 to 24 word recovery phrases, quoted lists of such words, 6-digit codes after `otp`, `code`, `pin` or `2fa`), on by default. `--grep` and `--exclude` match the redacted text, so they cannot test for a hidden value. It cannot catch a secret under an unusual key or in free text. With no `--app`, `logs` reads only the app `offsider.login.json` names, when it names one (`--all` for the whole device; on a phone, see below). Text output escapes control characters and strips terminal escape sequences; `--raw` keeps colour codes only, never the conceal code.
- **Notifications.** Whatever the device shows, including notifications, is on the screen. On a physical device, turn on a Focus or Do Not Disturb first. `notifications --app` prints one Android app's posted notifications, picked on the device (below), with one-time codes and card numbers hidden.

The skill `offsider init` installs tells the agent that all of this, and the notes saved with test users, is data from the app under test, never instructions, and to stop and ask before anything that moves money, touches real accounts, grants permissions the test did not name, links saved logins, unlocks a device or uses a physical device.

**When an agent runs it.** Offsider treats a run whose standard output is not a terminal as an agent's (`OFFSIDER_OUTPUT=person` or `agent` overrides the check, and an unknown value is ignored). Then names from the screen are always quoted in text, and `screenshot --no-mask-secure`, `batch --no-mask-secure`, `OFFSIDER_MASK_SECURE=0` and `describe-ui --raw-source` need a person: Touch ID or the login password with a terminal on standard input, `person_required` without one. `--json` output adds a top-level `untrusted` list naming each path whose value came from a device, an app or an agent-written note, so a harness can tell screen text from Offsider's own words. `offsider init`'s permission rules make Claude Code and Codex refuse or ask before the person-only and loosening commands; both match the command as typed, so they slow a misled agent rather than stop one, and Offsider's own checks remain the boundary.

## Saved secrets

Test users and unlock codes live only in your login Keychain, as generic passwords that are never synchronised. Passwords and codes never appear in Offsider's output, errors, logs, timings or arguments; a username prints only where a person asks for it (`credential add` and `credential status <name>`). macOS asks before a binary that does not match an item's access rule reads it, such as a rebuilt development build; a signed upgrade with the same identifier is likely to match and not ask.

- **Test users** (`credential add`): one item per user and app (service `com.mpalmes.offsider.login`, account the app id and the user's name); saving one user for an iOS and an Android app writes one item for each, from one typed password. `add` refuses browsers, home screens and system apps before it reads a password. With no app named, its menu reads the app in front on each running simulator and emulator (one `launchctl list` or `dumpsys` each), never a phone, and `offsider.login.json`; it reads the device allow-list file, without its Keychain seal, only to decide whether to ask about phones. Its encrypted data (version 2) holds the username, the password, the apps linked to it and its settings: `devices` (`virtual`, the default, for simulators and emulators only, or `any`, which also allows Android phones on the allow-list), `confirm` and `webLogin`. A version 1 item reads as no links, no confirm, `devices virtual` and no web sign-in, and every save writes version 2.
- **Context** (tags and the `--about`, `--avoid` and `--state` notes) sits in the item's attributes, which the Keychain does not encrypt, so any process running as you can read it without a prompt. It refuses email-like text, control and bidi characters, and must never hold secrets or personal details. Agents may write the notes and later sessions read them back, so `--json` lists them as `untrusted` and the skill says to read them as data. `confirm` and `devices` are mirrored there so `login` can ask early, but only the encrypted data decides.
- **Linking** (`credential join`): a person only. It needs a terminal on standard input, always asks which app to share with, asks Link or Cancel, then Touch ID or the login password, and refuses browsers, system apps and anything on the managed `deniedBundleIDs`. A link item for the second app id stores no password, only an index for a cheap lookup; `login` trusts a link only when the canonical item's encrypted data lists that app, which only `join` writes. Links saved by earlier versions, or planted in the index alone, are not trusted until `join` runs again; `join` then decrypts the shared app's users and, after the same prompts, writes the link into each one that lacks it. `credential remove` on a linked id unlinks it with no prompt, since it only takes access away: it removes the id from each user's encrypted links first and the index item last, so a failure part way still types nothing.
- **Loosening** a user (`--devices any`, `--no-confirm`, `--web-login`) needs a terminal and Touch ID or the login password; tightening needs neither.
- **The presence check.** A user saved with `--confirm` (on by default with `--devices any`) makes `login` ask for Touch ID, an Apple Watch or the login password before it reads the password; the macOS sheet names the user, the app and the device. It uses LocalAuthentication's device-owner check inside Offsider, because Keychain items that require user presence need the data protection keychain, which a command-line tool signed with Developer ID cannot use without a provisioning profile and an app bundle. With no GUI session (plain `ssh`) it fails closed with `person_required`.
- **`login`** types a password only into the app it was saved for or a person linked, and refuses: a browser or system app in front (`app_not_allowed`); a password field inside a web view, unless both the saved user (`--web-login`, by a person) and the repository's `offsider.login.json` (`"webLogin": true`) opt in; another app coming to the front before the password or before the submit tap (`foreground_changed`, recomputed from the tree it just read); a Cloudflare Turnstile widget (`turnstile_required`); a physical iPhone or iPad; and an Android phone that is not allowed or a user without `devices any`. On an iOS simulator, a web view is recognised by a web-area role or by a password field drawn by another process; with neither signal it is treated as native. Offsider never taps Turnstile: `turnstile` only reads its state, and the timing jitter it once had is gone.
- **Sign-in records** (`signins/`) hold the app, the app in front, the user's name, the platform, a stable device key, the time and a boot marker, never a username or password.
- **Unlock codes** (`unlock-code set`): service `com.mpalmes.offsider.unlock-code`, account the phone serial or AVD name. `set` needs a terminal; `set --stdin` still reads the code from a pipe but confirms on `/dev/tty` and with Touch ID or the password. On a phone it needs the phone to be allowed first. `wake --unlock` types the code once, as key events through the UiAutomation helper's authenticated socket, and only into a focused password field inside System UI's lock screen; without the helper it types nothing (`helper_unavailable`). It never becomes a process argument on the device. Before the first key, an empty `unlock/device-<id>.failed` marker is written (a write failure stops the command), and it is cleared only once the device is seen unlocked, so a failed code is never typed again until the device is unlocked by hand or the code is saved again.
- **The allow-list seal**: a login Keychain item (service `com.mpalmes.offsider.devices`, account `allowed-devices`, never synchronised) holding the SHA-256 of the allow-list.

## Simulators

- Xcode's private simulator frameworks (CoreSimulator, SimulatorKit and related) load at runtime from the selected Xcode. Offsider first resolves `DEVELOPER_DIR` or `xcode-select` with `realpath`, requires `<name>.app/Contents/Developer`, and checks that the app satisfies `anchor apple`, or, for Xcode from the Mac App Store, whose app the store signs, Apple's Mac App Store signature on `com.apple.dt.Xcode` with Apple's team identifier, read from the signature because the store's certificate names no team (its main executable and `Info.plist`, about 40 ms, once per process), refusing with `xcode_unusable` otherwise; `doctor` reports it as `xcode.trust`. The check proves the app's main executable and `Info.plist` are Apple's; library validation is what stops a non-Apple framework loading into the signed binary. `devicectl` and `xcodebuild` run only from a trusted Xcode too.
- Before each private Objective-C method it calls through a cast, Offsider compares the method's type encoding with the one it recorded, and fails with `xcode_unusable` rather than call a changed method or one it has no record for. C functions it finds with `dlsym` carry no encoding, so they are not checked. `doctor`'s `xcode.private-api` runs the same comparison ahead of time and warns when CoreDevice is newer than the last version tested.
- Simulator HID input (touches, key presses, buttons and text) goes to the simulator named with `--device`, through a broker on a per-user Unix socket under `$TMPDIR/offsider-hid-<uid>`: `offsider` started detached in its own session, one per simulator, holding the simulator's input session so later commands skip opening it. The broker rejects connections from any other user, and from any process that does not satisfy its own code signature's designated requirement (checked once per connection; a release build accepts any Offsider of the same team and identifier, a development build only itself), before sending them anything, serves at most 32 commands at once, gives each request 2 s to arrive whole once its first byte has, passes their input to the simulator one request at a time, and refuses a request of more than 65,536 events, a coordinate that is not finite or beyond ±100,000, a pause that is not finite or is outside 0 to 3600 s, or pauses over 3600 s together. When a command goes mid-request it stops within 100 ms, and it lifts any touch, key or button a command leaves down; `touch --down` alone stays down until a later `touch --up`. It closes a command that sends nothing for the idle time while holding nothing down, and input too long for it (over 65,536 events) goes through the command's own session. It stops 60 s after the last command (`OFFSIDER_SIMULATOR_SESSION_IDLE`, at most 3600), when the simulator restarts, on `offsider session stop`, or at its next idle moment once 12 hours old, and logs only its start and why it stopped. When input fails it stops too, after input already queued finishes, and the commands still attached open sessions of their own. `OFFSIDER_SIMULATOR_SESSION=off` opens an input session for each command instead, though `touch --down` or `--up` alone still uses the broker. A command the broker closes before its handshake cannot ask who closed it, so it finds the broker among this user's `offsider` processes by its arguments (`hid-broker --udid <udid>`) and the socket it holds, checks that process's code the same way, and stops it (SIGTERM) only when it is another Offsider build's, then starts its own; a broker of this build is never stopped that way.

## Android emulators and phones

- **The helper.** A small helper, Offsider's own code built from the Java source in this repository, reads the screen through UiAutomation and can inject input. Its dex is pushed 0600 into a 0700 folder made by the shell user, `/data/local/tmp/offsider-push-<pid>`, then moved to its content-addressed name, `offsider-helper-<hash>.dex`, made 644 and the folder removed, so it is never writable by others. On every start the start script checks the copy's SHA-256 against the manifest (`sha256sum`), and only on an image without `sha256sum` falls back to its size. The Mac's copy is checked against the digest compiled into Offsider. The helper runs with `app_process` as the shell user, listens on a randomly named local socket, accepts one connection only from the shell or root user and only when the first message carries a random token printed only on the shell stream that started it, then stops listening. It exits when that connection or its shell closes, or after 10 s without a request (30 s for a warm helper, whose broker pings it every 2 s). While it runs it holds Android's single UiAutomation slot, and the device reports an accessibility service as enabled. When it cannot run, a temporary `uiautomator` dump under `/data/local/tmp` is read and deleted instead.
- **The warm helper.** On an emulator, and on an allowed USB phone only with `OFFSIDER_ANDROID_SESSION=on`, the helper outlives the command, so the next one skips its start and the wait for a quiet screen. A broker keeps it: `offsider` started detached in its own session, holding the helper's start shell and its one connection, so the token stays in the broker's memory and never reaches a disk. Commands reach the broker on a 0600 Unix socket in `sessions/`, which refuses other users (`getpeereid`) and any process that does not satisfy its own code signature's designated requirement, as the simulator and iPhone brokers do, serves at most 8 commands at once and passes their requests to the helper one at a time; it refuses `quit`, never sends input whose command has gone or that waited over 4 s behind another command, and gives up on the helper when a command's own timeout passes, counted from when its request arrived. It stops 60 s after the last command (`OFFSIDER_ANDROID_SESSION_IDLE`, at most 3600), on `offsider session stop`, when the helper misses its ping, or at its next idle moment once 12 hours old, and stopping it ends the helper, which frees the slot. Until then Appium, Maestro, `uiautomator`, instrumentation tests and Layout Inspector cannot connect, and apps can see an accessibility service enabled. A command that reads the screen another way (`OFFSIDER_ANDROID_TREE=uiautomator`, `OFFSIDER_ANDROID_SESSION=off`, a phone without `on`) stops Offsider's own warm helper on that device first, once no other command is using it, and removing a phone from the allow-list stops its one. Passwords and unlock codes typed through the helper pass through the broker's memory and are never logged. For an emulator with one display it also keeps, in memory only, the device states and display list a command read, which later commands reuse instead of reading them again. A command or `session stop` it closes before a byte finds it by its arguments (`android-session serve --device <serial>`) and the socket it holds, and stops it the same way, only when it is another build's. `OFFSIDER_ANDROID_SESSION=off` keeps one helper per command.
- **Typing secrets.** A password from `login`, any text typed into a focused password field without gRPC, and text from `--stdin`, `--file` or a batch step into a field whose focus cannot be read, goes through the helper as key events, never as an `input text` command that other shell-user processes could see in the process list; without the helper nothing is typed. A clipboard paste is refused for a password field and for a field whose focus cannot be read. Over gRPC, non-ASCII text is pasted through the emulator's clipboard, which is restored afterwards; whether the emulator's clipboard sharing copies a paste to the Mac's pasteboard has not been checked.
- **gRPC.** The emulator's endpoint on loopback is authenticated with the token from the emulator's discovery file, or with a short-lived JWT: Offsider keeps the private key in memory and writes only the matching public key to the emulator's `jwks` folder, deleting it when the command ends; a key left by a killed command is removed by the next one.
- **Booting.** `offsider boot` starts the SDK's emulator with `-no-metrics`, never `-port` or `-grpc`. `--emulator-arg` accepts only an allow-list of flags that shape the device or its rendering, each value checked; flags that open a listener, connect out, read a host path or send metrics are refused, as are Offsider's own flags and `@name` tokens. `-camera-back` and `-camera-front` take only `emulated` or `none`, so an agent cannot see through the Mac's camera; an AVD's own `config.ini` can still name a webcam. Offsider never uses Google's Android CLI and never bundles adb.
- **State that persists.** `stay-awake` writes the `stay_on_while_plugged_in` global setting; `wake` sends `KEYCODE_WAKEUP` and `wm dismiss-keyguard`; `permission`, `status-bar`, `appearance`, `content-size` and `orientation` change settings that outlive the command.
- **Phones.** A USB phone is refused until a person allows it (below). An allowed phone's setters change the phone itself: `status-bar override` and `stay-awake on` say so with the undo command, `permission ... all` is refused, since it would reach SMS, the call log and location, and `permission --app` must name an allowed app that is not on the deny-list. Wi-Fi and TCP adb connections are refused, as is a USB device reporting an emulator's serial; when adb cannot list devices, an `emulator-N` serial is refused rather than trusted. Offsider never sets `adb reverse`.
- **The app in front.** The deny-list holds browsers and system apps (Settings, System UI, Chrome and its channels, Firefox, Samsung Internet and Samsung's system apps, Gmail, Outlook, Messages, Play Store, Google Play services, Photos, Contacts, the dialer, the permission controller, the package installer, Wallet, password managers, authenticator apps and Find My Device), matched by exact id or by prefix, plus any managed `deniedBundleIDs`. With such an app in front, an app outside the allowance, or an app Offsider cannot name: a screen read, a screenshot, a video frame (read at most once a second) and every input step are refused (`app_not_allowed`), the app in front being read again before each input step and before a capture that follows input. Buttons are not checked, so a phone can always be sent home, and a finger already down is not checked again for its move or lift. A screen read also checks the active window, so the notification shade or quick settings open over the app are refused; a screenshot or coordinate input without a tree read relies on the resumed activity alone, which the shade does not change.
- **Notifications on a phone.** `notifications` reads one allowed app at a time and picks its records on the device: on Android 11 and later by key (`cmd notification list`, keeping keys whose package field is the app's, then `get` for each), so another app's notification text never reaches the Mac; on Android 8 to 10 by a shell filter over `dumpsys notification --noredact` that keeps the app's records in the active list. That filter works line by line, and notification text can hold line breaks, so a notification whose text imitates a record header for the allowed app can carry the rest of its own record past it. Values are redacted as screen text is.
- **Logs on a phone.** `logs` reads one allowed app at a time (`--app`, else the single pin, else `offsider.login.json`'s package when allowed). The whole device's log (`--all`, `--process`, or no app) needs the allowance "Any app and all logs", which only a person chooses.

## Physical devices: the allow-list

- Every command that names a physical iPhone, iPad or Android phone checks the allow-list first and refuses with `device_not_allowed` (exit 7), sending the device nothing: an iPhone is refused before any `devicectl` call, a phone after reading only the adb server's own device list. `list-devices` hides such rows unless `--physical` is passed. A physical device must be named with `--device` on each command; `OFFSIDER_DEVICE` never names one. Each command that drives an allowed device prints one line to stderr naming it, its expiry and how to withdraw it.
- `offsider devices add` is the only way onto the list. It needs a terminal on standard input (without one it is `person_required`), explains what it grants, lets a person choose the device, its team, the app to pin and the expiry from menus, shows a summary, then asks for Touch ID or the login password. Building those menus adds two local reads. The team menu lists the code-signing identities in the login Keychain: identities only, never private keys, and with no prompt. The app menu sends one installed-apps query to the chosen device (and, on an Android phone, one read of the app in front), only after the person picked it in the menu and before Touch ID: a deliberate trade-off, so an agent driving a pseudo-terminal can list a phone's apps without allowing it. A failed query falls back to typing an app id. Deny-listed apps and apps outside a managed ceiling are not offered. One app is preselected (`offsider.login.json`'s app when installed, else on Android the app in front); "Any app" is never preselected and says it includes banking and messages, and on Android "Any app and all logs" (stored as `*`) also allows whole-device logs. A device passed with `--device` gets the same summary, naming the device by its model, and the same Touch ID; it is no longer asked for the last four characters of its ID, which a person copying a pasted command could copy too. Entries expire (12 hours by default, at most 30 days unless `never`), can pin the apps Offsider may drive (with none, each command drives only the app it names, on every platform), and for an iPhone or iPad can record the team that signs its runner. The parser is strict, so an older Offsider refuses a list holding a team. `remove` needs no terminal, and on an iPhone or iPad also stops its runner and session broker, deletes `runner.log`, and offers to uninstall the runner (or prints the command off a terminal).
- The list is sealed: `add` and `remove` store the file's SHA-256 in the login Keychain, and an edit made any other way, or a missing seal beside a non-empty file, refuses every device until a person runs `add` again. This turns a quiet file edit into a deliberate Keychain write; a hostile process running as the same user can still delete and re-add the item.
- Managed preferences in the domain `com.mpalmes.offsider`, honoured only when forced by a configuration profile, set a ceiling an administrator controls: `allowPhysicalDevices`, `allowedDeviceIDs` and `allowedBundleIDs`, and `deniedBundleIDs`, which extends the deny-list for `login`, `credential join` and every physical device (an entry ending in `.` is a prefix). A forced key of the wrong type refuses every physical device. Both the managed ceiling and the user's list must allow a device; only the managed preference is beyond a process running as the user.
- The list, the seal and managed preferences are read only when a command names a physical device, once per process, and never cached on disk.

## iPhones and iPads

- **Connection.** USB only: only a wired transport passes, and before each input batch usbmuxd must still list the device on USB. Offsider never pairs a device, never accepts a prompt on it and never types a passcode.
- **One app.** Each command drives one app: `--app`, else `offsider.login.json`'s `bundleId`, else the allowance's only pinned app. It must not be a browser or system app (by id or prefix, Gmail, Outlook, password managers, authenticators and Find My included, plus any managed `deniedBundleIDs`) and must be within the allowance's apps and any managed `allowedBundleIDs`. Before each screenshot, broker or video frame, each input batch and each detached touch, the runner checks with XCTest's own active-app lookup that the app is in front (with an Xcode that no longer has the lookup, as 27.1, with the app's own foreground state, which may miss a system alert or Control Center over the app and passes for an app sharing the screen in Split View or Stage Manager), and the command stops with `app_not_allowed` before reading or touching the screen otherwise. A confirmation is reused for up to 2 s within one command only while no input is sent: any input clears it, so a capture after a tap checks again.
- **Android pins.** An Android phone's allowance can pin apps too (the app step of `devices add`, or `--app <package>`), narrowed by any managed `allowedBundleIDs`: with a non-empty set, the checks above refuse another app in front with `app_not_allowed`, naming the allow command, or saying the managed ceiling cannot be overridden. With no pins, each command drives only the app it names (`--app`, else `offsider.login.json`'s `package`) and refuses with neither.
- **The runner.** The accessibility tree comes from a small XCUITest runner app built from source bundled with Offsider into `~/Library/Caches/offsider/runner/` (0700). Each source file copied into the cache is checked against the digests compiled into Offsider.
- **Its team.** It is signed only by the team a person recorded in `devices add`, by picking it from the menu of the login Keychain's signing identities or typing it (`--team` in scripts), or, when the allowance names none, the team in `OFFSIDER_IOS_TEAM_ID`; a variable naming another team than the allowance's is refused. Xcode's signed-in team is never picked silently, only by a person in that menu. Its bundle ids are `<prefix>.runner` and `<prefix>.runner.uitests`, with the prefix from `OFFSIDER_IOS_RUNNER_PREFIX` (default `com.mpalmes.offsider`, validated); the first build under any other prefix creates App IDs in the team, so only `offsider runner build --device <UDID>`, confirmed by a person at a terminal with Touch ID or the login password, may do it, and the approved prefix is remembered. Normal builds never let Xcode register a device with the team; only `offsider runner build --device <UDID> --register-device`, which needs a terminal on standard input and output and Touch ID or the login password, does. Builds still pass `-allowProvisioningUpdates`, so Xcode creates or renews the runner's App IDs and profiles in that team without asking.
- **Its products.** After a build, `products.json` (0600) records the device, team, prefix and the SHA-256 of each product. Before each session starts, the products are hashed again, and the host app, the runner app and the `.xctest` bundle must satisfy `anchor apple generic and certificate leaf[subject.OU] = "<team>"` with their resources validated; otherwise the build is deleted and rebuilt once, then refused.
- **Running it.** It is launched detached with `xcodebuild test-without-building -quiet`, listens only on the device's loopback with a token per session, and is reached only through usbmuxd (`/var/run/usbmuxd`). Offsider's session record (pid, port and token, 0600), `runner.log` and result bundles live under `ios-devices/<UDID>/`; the token is never printed, and result bundles are deleted when a session stops or an exited one is forgotten.
- **The session broker** (Xcode 27) holds the device's CoreDevice screen stream, its UniversalHID touchscreen and keyboard and its hardware button socket. It listens on a 0600 Unix socket in `sessions/` and refuses other users and any process that does not satisfy its own code signature's designated requirement, as the HID broker does. Every 30 s it reads the device's allowance again (the file, its seal and managed policy) and asks usbmuxd whether the device is still on USB, and when either fails it ends the stream, releases any held touch, key or button and stops. It serves at most 8 clients at once, drops a client that sends no first request within 10 s, is then silent for the idle timeout or takes more than 10 s to send a started request, refuses a request with more than 4,096 steps, a wait that is not finite or is outside 0 to 30 s, or waits over 60 s together, caps swipes at 1,000 steps and 30 s, refuses frame sizes over 16,384 pixels a side, and presses only the home, lock, side and Siri button usages. Its screen stream reaches the Mac only through CoreDevice's USB tunnel, and the device shows its screen-sharing indicator while it runs.
- **Lifetime.** The runner and the broker stop after `OFFSIDER_IOS_RUNNER_IDLE` and `OFFSIDER_IOS_SESSION_IDLE` seconds without a request (default 300, at most 3600). A runner session older than 12 hours is restarted on its next use, and a broker older than 12 hours stops at its next idle moment.
- **The developer disk image.** Any device command's wake step asks CoreDevice for `ddiServices`, which mounts a missing developer disk image, and `doctor --fix` mounts one too; both happen only on an allowed device named with `--device`.
- **What stays.** `session stop` stops the broker and the runner, clears the screen-sharing indicator and deletes `runner.log`; the runner apps stay installed and the cache stays. `session stop --clean` (or `runner stop --clean`), which also works once the device's allowance has expired or been removed when this Mac holds its runner build or session record, also uninstalls `<prefix>.runner.uitests.xctrunner` and `<prefix>.runner`, and deletes this device's runner builds, `runner.log` and the broker's log. What only the Apple developer site (Certificates, Identifiers & Profiles) removes stays in your team: the runner's provisioning profile, its App IDs and the device's registration.

## Release integrity

- Releases are built by `.github/workflows/release.yml` in separate jobs. The build job holds no secrets: it checks the tag's signature against `main`'s `.github/allowed_signers` and that the tag is on `main`, builds the binary, the idb frameworks and the runner check, and packs an unsigned payload with its SHA-256. A signing job in the protected `release` environment, on a fresh runner, checks out the tag commit, verifies the payload's digest, signs and notarises it, and never builds or runs it; the signing keychain and the notary key are removed as soon as each is used. A verify job on another fresh runner, with no environment, unpacks the signed archive, verifies the signatures and notarisation, runs the signed binary through commands that load CoreSimulator and SimulatorKit and fails on any library validation rejection in the system log, and runs the Homebrew gate. Only then is the release published with its `SHA256SUMS` and a GitHub build provenance attestation.
- Release binaries are signed with a Developer ID certificate, use the hardened runtime and are notarised by Apple. Their entitlements, in [entitlements.plist](entitlements.plist), are empty: library validation is on, so the binary loads only frameworks signed by the same team or by Apple. Ad-hoc builds for local rehearsals use [entitlements-adhoc.plist](entitlements-adhoc.plist), which disables library validation because an ad-hoc signature has no team; `scripts/release.sh` refuses to sign a release with a file that disables it.
- The SHA-256 of every file in Offsider's resource bundle (the Android helper's dex and manifest, the skill, the guide topics and the runner's source) is compiled into the binary at build time. A file that differs is refused with `install_damaged`. A replaced binary loses its Developer ID signature, but nothing refuses to run it: a Homebrew install carries no quarantine flag, so Gatekeeper does not look again, and only macOS's Keychain access check and the brokers' signature check (a replaced binary is not the build a running broker serves) notice.
- The [install guide](docs/install.md#verified-tarball) shows how to check `SHA256SUMS` and the attestation, with `--signer-workflow` and `--source-ref` pinning it to the release workflow and the tag, and `--deny-self-hosted-runners`.
- The Homebrew formula is updated only through a pull request on the tap, opened by a GitHub App with access to that repository alone, and merged by auto-merge only after the tap's own checks pass. Those checks render the formula with `render_formula` from the tagged release's `scripts/release.sh` and fail on any byte of difference, a pull request touching other files, a URL other than the release's own, a prerelease or a downgrade, then install it after checking its SHA-256 and verifying its attestation with `--source-ref` and `--deny-self-hosted-runners`. The access token the App replaced is revoked once the App's first pull request has merged.
- A pull request's head commit must be signed by a key in the base branch's `allowed_signers`, whatever it changes (the `Protected paths signed` check, which runs the base branch's copy of its workflow), so an account taken over without that key can merge nothing.
- The idb frameworks are built from the [michael-palmes/idb](https://github.com/michael-palmes/idb) mirror at a pinned revision that `scripts/build.sh` verifies before building, and Swift package versions are resolved strictly from `Package.resolved`. The Android helper's dex is rebuilt from its source with a pinned toolchain and compared with the committed copy in CI.
- One maintainer holds admin rights on the repository. An admin account takeover could still change its rules; a hardware security key on the account is the backstop. Tags are signed with an SSH key listed in `allowed_signers`, which is not yet hardware-backed.

## Build hardening

- `OffsiderCore`, the pure logic every command uses, is compiled with Swift's strict memory safety checking, so each unsafe pointer, C string and C call is marked where it happens. The other targets are not yet.
- CI runs the unit tests under AddressSanitizer after each merge to main, and property tests feed the parsers seeded random and malformed input on every `swift test`.
- A weekly job fuzzes every parser that reads device, daemon or file bytes (adb, the helper's frames, usbmux, screenshots, uiautomator dumps, the media stream answer, the tree cache, the allow-list, the mask file, JSON and the log redactor) under AddressSanitizer. It is a mutation fuzzer, not coverage guided, since Xcode's toolchain ships no libFuzzer runtime.
