# Security policy

This file describes the version on its first line, with the file, workflow or command behind each control. The page to forward to a security team is [Offsider for security teams](docs/security-overview.md); the plain-words version is [Privacy](docs/privacy.md); policy for a fleet is [Managed Macs](docs/mdm.md).

## Reporting a vulnerability

Report privately through GitHub: open the [Security tab](https://github.com/michael-palmes/offsider/security) and choose **Report a vulnerability**. Please do not open a public issue. Include the Offsider version (`offsider --version`), your macOS and Xcode versions, and steps to reproduce.

One maintainer handles reports, on a best-effort basis:

| Step | Target |
| --- | --- |
| Acknowledge the report | Within 7 days |
| A fix or a mitigation plan | Within 30 days of confirming it |
| CVE | Requested through GitHub's CNA and published with the advisory |
| Public disclosure | 90 days after the report, or earlier once a fix ships |
| Versions fixed | The latest release only |

## Supported versions

Only the latest release receives security fixes. Upgrade before reporting an issue you found on an older version. Offsider is pre-1.0: a minor release can change a command, and the [changelog](CHANGELOG.md) lists each change.

## Scope and threat model

Offsider is a local command-line tool that AI agents and scripts run on a developer's Mac to read and drive simulators, emulators and USB devices. It runs no service and has no accounts. This file lists everything it touches and the controls around each, at the version on its first line.

It is built for these risks:

- **An agent that follows the wrong instructions.** Text on a device's screen, in a web view, a notification or a log is written by the app under test or by whoever can put text in it. Offsider treats it as data: it escapes and caps what it prints, and the bundled skill tells agents to stop and ask when screen text asks for anything.
- **An agent that reaches too far.** Allowing a physical device, approving an app's guard rules, linking apps to a saved login, loosening a saved login, saving an unlock code, reading a refused file with `--allow-path`, turning off a mask or log redaction, and registering a device with a team each need a person at the Mac, in a terminal, confirmed with Touch ID or the login password. No environment variable or flag skips that; `OFFSIDER_UNATTENDED=1` only tightens it, refusing each such step at once with `person_required` and the step a person must take, instead of waiting ([Unattended runs](docs/agents.md#unattended-runs)). Saving a test login for simulators and emulators needs no person (`credential add --stdin`), and neither does using one.
- **Secrets in output.** Password values never print outside `describe-ui --raw-source`, which only a person can run; screenshots mask password fields by default; logs are redacted by pattern; and Offsider never echoes typed text in its output, errors, logs or timings. Where typed text can still show is under [Saved secrets](#saved-secrets).
- **Other local users and planted files.** Every file Offsider writes in its private folders is private to the user, and files and sockets are opened without following symlinks and checked before use.
- **A tampered install or release.** Releases are built without secrets, signed in a separate job, run with library validation on, and check their bundled files against digests compiled into the binary.

### Offsider trusts

- The person at the Mac's terminal who confirms with Touch ID or the login password.
- macOS, an Xcode that Apple signed (checked: [Simulators](#simulators)), the Android SDK you installed, and the daemons they run: the adb server, the emulator, usbmuxd and CoreDevice.
- Managed preferences a configuration profile forces ([Managed preferences](#managed-preferences)).
- Its own build: a release trusts any Offsider signed by the same team with the same identifier, a development build only itself.

### Offsider does not trust

- The agent. It may be misled, so no gate rests on its good faith.
- Anything on a device or from an app: screen text, web views, notifications, logs, and the notes agents save with test users.
- Other local users.
- Other builds of Offsider, and any other program that connects to its sockets.
- Files other programs write that Offsider reads.

### Not a security issue

- **A hostile process already running as you.** It can read your files and the Keychain items you can read, and drive any device itself. Offsider's controls make its own path harder, not that one; where a control only raises the bar against such a process, this file says so.
- **A person allowing a device for an agent.** `devices add` is that person's consent; what an agent does inside the allowance is what they allowed.
- **The effects of commands an agent may run.** A tap the agent chose, a setting it changed or a simulator permission it granted.
- **Your agent's own behaviour,** its network use and storage, and what it sends its model provider.

## Network

Offsider has no telemetry, no accounts and no update checks. It talks only to this Mac and to devices on its USB cable: Unix sockets, loopback (127.0.0.1 and ::1) to the adb server, the Android Emulator's gRPC endpoint, usbmuxd and Metro, and for a wired iPhone or iPad, CoreDevice's own services and screen stream over the device's USB tunnel. Offsider's own code resolves no hostnames; the Apple tools it runs, such as `xcodebuild` and `devicectl`, reach Apple themselves.

| Path | When | Destination | What goes | Off switch | Control |
| --- | --- | --- | --- | --- | --- |
| adb server | Any Android command | 127.0.0.1 or ::1 over TCP, or a Unix socket | adb requests: device commands, the helper's dex push | Run no Android command | `Sources/OffsiderAndroid/Adb/LoopbackEndpoint.swift` |
| Emulator gRPC | Input and screenshots on an emulator | 127.0.0.1, else ::1, at the port in the emulator's discovery file | Input and screen reads, with its token or a short-lived JWT | `OFFSIDER_ANDROID_TRANSPORT=adb` | `Sources/OffsiderAndroid/Grpc/EmulatorControlClient.swift` |
| usbmuxd | Any iPhone or iPad command | `/var/run/usbmuxd`, then the USB cable | Runner requests with a per-session token | Run no iPhone or iPad command | `Sources/OffsiderIOSDevice/Usbmux/UsbmuxClient.swift` |
| CoreDevice | An iPhone or iPad session (Xcode 27) | The device, over its CoreDevice USB tunnel: a UDP socket on a `utun` address | Stream setup, then screen frames back; touch, key and button reports | `session stop` | `Sources/OffsiderIOSDevice/Stream/IOSDeviceScreenStream.swift` |
| Metro | `rn open` | 127.0.0.1 at the port you pass, then [::1] only to explain a Metro bound there | At most two `GET /status`, then one connection to read the port's owner before a reverse | Run no `rn open` | `Sources/Offsider/Utilities/MetroStatus.swift` |
| `xcodebuild` (Apple's) | Building the iPhone runner | Apple's developer services | Your team's App IDs and profiles; a device registration only when a person picks a team in `devices add` or runs `--register-device` | Build no runner | `Sources/OffsiderIOSDevice/Runner/RunnerBuilder.swift` |
| CoreDevice disk image (Apple's) | The first command on an iPhone without a developer disk image, or `doctor --fix` | May reach Apple to personalise the image, as Xcode does | What Apple's personalisation asks for | Mount it once from Xcode | `Sources/OffsiderIOSDevice/Directory/IOSDeviceDirectory.swift` |
| Homebrew | `brew install` | GitHub, and Homebrew's own analytics | Homebrew's install analytics | `brew analytics off`, or the [verified tarball](docs/install.md#verified-tarball) | Homebrew |
| Your agent | Whenever it runs Offsider | Its model provider | Whatever Offsider printed | Your agent's settings | Your agent |

- **Metro.** `rn open` reads `/status` on 127.0.0.1 at the port passed to it, and, only when that is silent, on [::1] to say Metro is bound there instead: each one HTTP request with a 2 s timeout, no proxy, and never a redirect (a 3xx reads as "something else answered"). Before it sets a phone's `adb reverse`, it connects to 127.0.0.1 once more to read which of your own processes holds the other end.
- **adb.** Over loopback TCP (127.0.0.1, ::1) or a Unix socket; `ADB_SERVER_SOCKET` or `ANDROID_ADB_SERVER_ADDRESS` naming anything but 127.0.0.1, ::1 or `localhost` (mapped to 127.0.0.1, never looked up) is refused, a `localfilesystem:` socket whose server runs as another user is refused (`getpeereid`), and so is a TCP port whose first connection in each command no process of yours accepted (another user's listener on 5037, found with `proc_pidfdinfo`). `doctor` names the program behind the port and warns when it is not the SDK's `adb`. Offsider starts the SDK's own adb with mDNS off (`ADB_MDNS=0`) when none is running, and that server keeps running afterwards like any adb server. A shell or exec command that prints more than 64 MB is stopped.
- **`xcodebuild`**, which builds the iPhone runner, talks to Apple's developer services for provisioning, as Xcode does; Offsider passes it only the proxy variables for that.
- **The developer disk image.** Mounting a missing one, which CoreDevice does on an iPhone's first command, may ask Apple to personalise it, as Xcode does. This has not been checked yet ([Not yet](#not-yet)).
- **The screen stream.** An iPhone or iPad session binds an IPv6 UDP socket on the Mac's `utun` address in the device tunnel's /64, scoped to that interface, and connects it to the device's tunnel address once the first packet arrives from there. macOS carries that tunnel over the USB cable; it is not loopback, and it is not the network.
- **Why `nm` lists `getaddrinfo`.** SwiftNIO, linked for the emulator's gRPC, carries a resolver. Every address Offsider dials is a loopback literal (the files in the table above); a source test that pins this is in [Not yet](#not-yet).

Check it while a command runs: `lsof -nP -i -a -c offsider` shows loopback only, and an iPhone session adds its sockets on the CoreDevice tunnel (the screen stream's UDP socket and the connections CoreDevice hands over for input); `lsof -nP -U -a -c offsider` shows the Unix sockets.

## On the Mac

Offsider keeps its state in a private per-user directory, `offsider-<uid>/` under the per-user temp directory from `confstr(_CS_DARWIN_USER_TEMP_DIR)`, which ignores `TMPDIR` (falling back to `$TMPDIR/offsider-<uid>/` when it cannot be used). It is mode 0700, owned by the user and checked on every use. Every file Offsider writes there itself is 0600: records go to a fresh file renamed into place, and lock files are opened in place without following symlinks. Files `xcodebuild` and `devicectl` write under `ios-devices/` keep those tools' modes, inside 0700 folders. A private file is read only when it is a regular file owned by the user, opened without following symlinks and without blocking, so a FIFO planted in its place is refused rather than hanging a command.

- `locks/`: one file per device driven, holding only the holding command's pid, name and start time. The lock is advisory and never inherited by the processes Offsider starts. While `record-video` runs, a `<platform>-<id>.recording` marker beside it stops `login`, `wake --unlock`, and `type --stdin` or `--file` with a password field on screen; `record-video` will not start while one of those holds the device.
- `trees/`: the last accessibility tree read from each device, named by the first 16 hex digits of a SHA-256 of the platform and device ID, so device names never reach a file name. It holds the tree as `describe-ui` prints it without the `native` attributes (no process IDs or class names), with password values, revealed password fields, the elements the evidence run's and `offsider.mask.json`'s masks name with what is nested in them, and parents' copies of that text already hidden, plus the writing command, timestamps, the screen's size, rotation, display and posture, and a boot marker. It is capped at 1 MB, ignored from an earlier boot of the device, and deleted once 10 minutes old by the next command that reads or writes the cache, whichever device it belongs to. Beside it, `<hash>.secure.json` records the id and frame of up to 32 password fields, so a field a show-password toggle turned into plain text is still hidden; it is swept with the tree. It may also hold the last tree seen before a modal covered the app, masked the same way, for at most 2 minutes unless a later read confirmed it, so a screenshot behind an iOS sheet can still be masked. Toasts are never cached. For an iOS simulator, `<hash>.frame.json`, named by a hash of the device ID, holds digests of the last screenshot and its elements for the frozen display warning, never a label or value. The cache serves `describe-ui --diff`, verify change lists and the tap guard, and is never sent anywhere. `OFFSIDER_TREE_CACHE=off` turns it off.
- `leases/` (each record beside a `.lock` file), `runs/`, `signins/`, `orientation/`, `displays/`, `postures/`, `reverses/`, `airplane/`, `unlock/`, `turnstile/` and `adb/`: lease records, evidence run records, sign-in records, Android auto-rotate records, foldable phone panels, foldable phone overrides, Metro reverse records, airplane mode records, unlock code markers, the last Cloudflare Turnstile state per device (dropped after a day) and the pid of the adb server last found to be yours, a hint for the next owner check, which still checks it. None holds a username, password, code or screen text.
- `captures/`: screenshots taken with no `--output` and no evidence run inside a git checkout, so they never land in the repository.
- `logs/`: the emulator's output from `boot`, `boot-<avd>.log` (the AVD name made safe for a file name), emptied once it passes 5 MB.
- `ios-devices/<UDID>/`: iPhone and iPad runner and broker records and logs ([iPhones and iPads](#iphones-and-ipads)).
- `sessions/`: the brokers' sockets and logs. The iPhone session broker's socket; each Android device's warm helper socket and log, `android-<hash>.sock` and `.log`, named by a hash of the serial; and each simulator input broker's log, `simulator-<hash>.log`, named by a hash of the UDID. Every broker log is opened 0600 without following symlinks and emptied once it passes 5 MB.

Outside it:

- `$TMPDIR/offsider-hid-<uid>/`: the simulator input broker's per-user Unix sockets and their lock files ([Simulators](#simulators)). It follows `TMPDIR`.
- `~/.config/offsider/allowed-devices.json`, the allow-list of physical devices, beside its `.allowed-devices.lock` ([Physical devices: the allow-list](#physical-devices-the-allow-list)). The folder is 0700 and the file 0600, written atomically under the lock, read with a 64 KiB cap. Its path comes from the password database (`getpwuid_r`), never `HOME` or `XDG_CONFIG_HOME`; a `~/.config` symlink is followed once, and only to a folder the user owns that others cannot write.
- `~/.config/offsider/device-audit.log`, the audit trail of physical-device commands, and `device-audit.log.1`, the 5 MB before it. Every command that drives a physical device, is refused on one or changes who may drive one appends one JSON line: the time, the Offsider version, the command path, the device as a 16-digit hash, the app id, the outcome, the exit code and reason, never an argument, typed text, a device name or anything read from a screen. Each line carries the SHA-256 of the line before it, so an edit or a removed line shows (`doctor`'s `audit.chain`); lines cut from the end do not, and a process running as you can delete the file, so the same fields also go to the unified log (subsystem `com.mpalmes.offsider`, category `device-audit`, the app id hashed), which such a process cannot rewrite. The file is 0600, appended under a lock without following a symlink, and there is no switch that turns it off ([Audit trail](docs/device-access.md#audit-trail)). Simulators and emulators write nothing.
- `~/.config/offsider/guards.json`, the app guard rules a person approved, beside its `.guards.lock`: 0600, written atomically under the lock, read with a 1 MiB cap, and sealed in the login Keychain ([App guard](#app-guard)).
- The login Keychain: saved test users and their link items, unlock codes, the allow-list's seal and the guard approvals' seal ([Saved secrets](#saved-secrets)).
- In the per-user temp folder, short-lived files deleted once read: an unmasked simulator capture (`offsider-screenshot-<uuid>.png`) before it is masked, and a display list (`offsider-displays-<uuid>.json`).
- `~/Library/Caches/offsider/runner/`: the iPhone runner's build and `approved-prefixes`, the bundle prefixes a person approved, sealed by a login Keychain item (`com.mpalmes.offsider.runner`) ([iPhones and iPads](#iphones-and-ipads)).
- The emulator's `jwks` folder: with `OFFSIDER_ANDROID_GRPC_AUTH=jwt`, one public key, deleted when the command exits, or by the next one if it was interrupted.
- Files you ask for. Screenshots, diffs and recordings are written 0600 to `--output`, or to a generated name in the current directory, or in the private `captures/` when that directory is a git checkout. A generated name never replaces a file (a taken name gets ` 2`, ` 3` and so on), and the device name in it loses separators, control, bidi and zero-width characters. `--output` naming an existing file replaces it whole, through a sibling temporary file, `fsync` and rename, only when it is a regular image or video file the user owns; a link, a directory or another kind of file is refused, and nothing is deleted first. `record-video` writes into a private 0700 staging folder beside the target.
- Evidence run folders, after `offsider run start <dir>`: created 0700 with a `.gitignore` of `*` and a `.metadata_never_index`, so Spotlight does not index the captures, holding `run.json`, `manifest.ndjson`, a lock file and the captures, each 0600. A run whose recorded folder is no longer a real directory the user owns that others cannot write, holding that run's `run.json`, is refused (`run_unavailable`). A run stops recording 7 days after `run start` (`--expires <n>d`, at most 30); nothing deletes a run folder.
- `type --file` and `batch --file` read one regular UTF-8 file of at most 64 KiB, judged after symlinks resolve, opened without blocking (a FIFO is refused) and checked to be the file that was resolved. Files under `~/.ssh`, `~/.aws`, `~/.config`, `~/.gnupg`, `~/.docker`, `~/.kube`, `~/Library/Keychains`, `~/Library/Application Support/offsider` and `/etc`, and names such as `.env`, `.env.*` (not `.env.example`), `.netrc`, `.git-credentials`, `.npmrc`, `.pypirc`, `id_*`, `*.pem`, `*.p12` and `*.key`, and `~/.android/adbkey`, shell history files, `*.jks`, `*.keystore`, `credentials*.json` and `*.tfstate`, are refused. `--allow-path` lifts that only after a person confirms the resolved path with Touch ID or the login password at a terminal (`person_required` without one), and only while the name still resolves to that path; a batch's `type --file` step reads such a file only when `batch --allow-path` confirmed it. Every read prints the resolved path and size to stderr.
- `offsider init` writes its skill to `~/.claude/skills/offsider`, `~/.agents/skills/offsider` or the directory you pass with `--dest`. For an agent whose folder already exists it also merges permission rules into `~/.claude/settings.json` (only `permissions.ask` gains entries, and Offsider's earlier deny rules come out; other keys keep their values) or writes `~/.codex/rules/offsider.rules`, through a 0600 temporary file and a rename, reading at most 1 MiB and leaving a malformed file as it is. It never creates either agent's folder. `init --uninstall` removes the skill and those rules.
- `offsider.mask.json`, `offsider.login.json` and `offsider.guard.json` are read from the working directory up to the repository root, at most once per command, capped (64 KiB for the mask and guard files), as regular files, following a symlink only inside the folder.
- Files other programs write that Offsider reads, such as the emulator's discovery and `.ini` files, its boot log and the evidence manifest, are opened without following symlinks and without blocking, must be regular files and are capped (1 MiB, 16 MiB for the manifest), so a FIFO or `/dev/zero` planted there reads as no file. A unit test fails on a new `FileManager.contents(atPath:)`, `Data(contentsOf:)` or `String(contentsOf:)` read in the sources outside a short, justified list (`Tests/UntrustedReadLintTests.swift`).

Processes Offsider starts get an allow-listed environment, never the caller's whole one: a base set (`HOME`, `PATH`, `TMPDIR`, `USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_*`, `__CF_USER_TEXT_ENCODING`) plus, per kind of child, `DEVELOPER_DIR` for short-lived Apple tools (`simctl`, `devicectl`, `xcode-select`, `open`), the Android SDK and AVD locations for the emulator (with `ADB_MDNS=0`, and `ANDROID_EMU_ENABLE_CRASH_REPORTING=0`, though the emulator does not document that variable, so its effect is unconfirmed), the SDK, key and socket settings for `adb start-server` and other adb calls (with `ADB_MDNS=0`, never `ADB_TRACE`), `DEVELOPER_DIR` and `OFFSIDER_*` for Offsider's own iPhone and simulator brokers, the SDK, key and adb server settings and `OFFSIDER_*` for its Android brokers (with `ADB_MDNS=0`), and `DEVELOPER_DIR`, Offsider's own `TEST_RUNNER_OFFSIDER_*` (never the caller's other `TEST_RUNNER_*`, which xcodebuild would hand to the runner app) and the proxy variables for `xcodebuild` (`Sources/OffsiderCore/Platform/ChildEnvironment.swift`). A unit test fails on a new child process whose environment `ChildEnvironment` did not build. Detached children start in their own session with `POSIX_SPAWN_CLOEXEC_DEFAULT`, so they inherit no file descriptor but stdin (`/dev/null`), stdout and stderr; their logs are opened by Offsider without following symlinks, and must be regular, owned by the user and single-linked. The sockets Offsider opens or accepts itself (its brokers' listeners and connections, adb, usbmuxd, the iPhone runner and the screen stream) are close-on-exec as well, so a child that a library starts some other way does not inherit them. The emulator gRPC connection is not among them: Network.framework opens it. Every command turns off core dumps (soft and hard limit 0, so neither it nor a child it starts can raise them) before it parses its arguments, so no core file can hold frames, tokens, codes or typed text, and every broker (simulator input, Android helper and iPhone session) also keeps at most 256 open files before it opens any device or socket.

Every coordinate, delta and distance a command takes must be finite and within -100,000 to 100,000, and a display a device reports must be at most 16,384 pixels a side. Every decoder for device and daemon bytes (adb's shell and sync packets, the helper's frames, usbmux and the session broker) refuses a length over its cap at the header, before buffering anything.

`doctor` lists your other running `offsider` processes by reading each one's arguments and keeps only the subcommand and the `--device` value (or, without one, its `OFFSIDER_DEVICE`): never typed text, other arguments or other environment variables.

## What reaches your agent

Whatever Offsider prints reaches your agent, and from there whatever it sends to its model provider. Offsider itself sends nothing.

- **The screen, as text.** `describe-ui`, selectors, `wait`, `assert`, `--verify` change lists and errors carry the screen's labels, values, ids and window titles. Password values read as bullets, one per character. Control (C0, DEL, C1), bidi, zero-width (except the two joiners emoji need, U+200C and U+200D), soft hyphen, line and paragraph separator, interlinear annotation, tag and variation-selector characters in any of that text print as JSON-style escapes such as `\u001b`, so an OSC 52 clipboard write, hidden tag text or a payload smuggled in variation selectors shows inert (a lone U+FE0E or U+FE0F after a visible character, as every emoji label carries, stays as it is). A window title holding one is quoted, and screen text inside an error sentence is JSON-quoted, so a label cannot close the quote and finish the sentence. Each tree string (label, value, id, title) is cut at 500 characters (`…(+N)`) and at most 600 scalars, so a flood of combining marks cannot stretch one character; an `Error:` or `Try:` line, and a JSON error's `message` and `hint`, stop at 4,096 characters (`Sources/OffsiderCore/Terminal/TerminalText.swift`). An `Error:` line's continuation is indented, so screen text cannot start a line of its own. The `Try:` line holds only the error's `hint`, escaped the same way, and a hint never holds typed text, a password or an unlock code. JSON escapes the same characters (with `devices --json`, `doctor --json` and `describe-ui --raw-source` too) and still decodes to the original. A tree is cut at 64 levels or 50,000 elements, with a note.
- **Values in the tree.** `describe-ui`, `--verify` change lists and `wait` and `assert` output replace one-time codes after a keyword, card numbers, wallet addresses and recovery phrases in labels and values (never ids) with `[redacted ...]` markers, and count them; `--has-value` still compares the real text. A plain field at the id or frame where the cache last saw a password field (a show-password toggle) reads as bullets and counts as `revealed`, in all of these and in a `--has-value` miss, which says only `has a masked value`; without the tree cache there is no record and no such check. `offsider.mask.json` hides more by id, label, label text, value pattern or email, in trees, the cache, `--verify` lists, messages, notifications and screenshots: a match hides what is nested in it, and its text wherever a parent's label copies it. A file that cannot be used stops the command before anything reaches the device, so it never unmasks one. Redaction works by pattern, so a secret in another shape still shows.
- **The screen, as pixels.** Screenshots mask password fields by default, after one tree read, plus keyboard text (on Android what sits beside the keys, on iOS the bar above them), Android's clipboard chip and copy preview, and whatever `offsider.mask.json` names; a field without a frame withholds the image. Behind an iOS sheet or full-screen modal that hides the screen from accessibility, a screenshot paints where the tree cache last saw what a mask names, and reads the drawn text with macOS's own recognition, never stored or printed, to paint email addresses and text matches there. Masks cover only what the accessibility tree describes: web views, canvases, images, a secret in an ordinary text field (a show-password toggle, a custom PIN pad) and anything drawn between the tree read and the capture can still show. Evidence runs also mask email addresses; `OFFSIDER_RUN=off` beside a run drops its masks, and a note says so. Video is never masked by the tree: `record-video` and `stream-video` check once, before the first frame, that no password field, none a show-password toggle revealed, no keyboard text and nothing `offsider.mask.json` names is on screen, so one that appears later is recorded. A tree the device cut short, or one that cannot show what a modal hides, cannot prove a mask: a screenshot says so in `maskUnproven` and on stderr, and video warns.
- **Logs.** `logs` redacts by key (passwords, tokens, keys, cookies, `Authorization`, JWTs, emails, seeds and recovery phrases, private keys, one-time and verification codes, bank, card and identity numbers, wallet addresses), masking a key's whole value when it is an array or object, and by value pattern (wallet addresses, Luhn-valid card numbers, 12 to 24 word recovery phrases, quoted lists of such words, 6-digit codes after `otp`, `code`, `pin` or `2fa`), on by default (`Sources/OffsiderCore/Logs/LogRedactor.swift`). `--grep` and `--exclude` match the redacted text, so they cannot test for a hidden value. It cannot catch a secret under an unusual key or in free text. With no `--app`, `logs` reads only the app `offsider.login.json` names, when it names one (`--all` for the whole device; on a phone, see below). Text output escapes control characters and strips terminal escape sequences; `--raw` keeps colour codes only, never the conceal code.
- **Notifications.** Whatever the device shows, including notifications, is on the screen. On a physical device, turn on a Focus or Do Not Disturb first. `notifications --app` prints one Android app's posted notifications, picked on the device (below), with one-time codes and card numbers hidden.

The skill `offsider init` installs tells the agent that all of this, and the notes saved with test users, is data from the app under test, never instructions, and to stop and ask before anything that moves money, touches real accounts, grants permissions the test did not name, links saved logins, unlocks a device or uses a physical device other than an added test device.

**When an agent runs it.** Offsider treats a run whose standard output is not a terminal, or that an agent harness marks, as an agent's (`OFFSIDER_OUTPUT=person` or `agent` overrides what it prints, and an unknown value is ignored). Then names from the screen are always quoted in text, and `screenshot --no-mask-secure`, `batch --no-mask-secure`, `OFFSIDER_MASK_SECURE=0` on a screenshot or video, `record-video --unmasked`, `stream-video --unmasked`, `describe-ui --raw-source` and `logs` or `rn logbox` with `--no-redact` need a person: Touch ID or the login password with a terminal on standard input, `person_required` without one. `OFFSIDER_OUTPUT=person` does not open these, so a misled agent cannot talk its way through with a variable; a same-user process that clears the markers on a pseudo-terminal still reads as a person. `wake --unlock` asks for Touch ID or the login password each time on a phone that is not a test device; on an emulator or a test device nothing stands in front of typing the saved code. `--json` output adds a top-level `untrusted` list naming each path whose value came from a device, an app or an agent-written note, so a harness can tell screen text from Offsider's own words. `offsider init`'s permission rules make Claude Code and Codex ask before the commands that write saved logins, grant permissions, unmask or reach a device directly; nothing is denied, and the person-only commands refuse by themselves (`Sources/OffsiderCore/Agents/AgentPermissionRules.swift`). Both agents match the command as typed, so the rules slow a misled agent rather than stop one, and Offsider's own checks remain the boundary.

## Saved secrets

Test users and unlock codes live only in your login Keychain, as generic passwords that are never synchronised. Passwords and codes never appear in Offsider's output, errors, logs, timings or arguments. A username prints from `credential add`, and from `credential status <name>` for a person at a terminal; an agent reads `username: hidden`. macOS asks before a binary that does not match an item's access rule reads it, such as a rebuilt development build; a signed upgrade with the same identifier is likely to match and not ask. A locked Keychain is named (`keychain_locked`), and under `OFFSIDER_UNATTENDED` a read macOS would ask about refuses at once with `person_required` rather than raise a prompt.

- **Test users** (`credential add`): one item per user and app (service `com.mpalmes.offsider.login`, account the app id and the user's name); saving one user for an iOS and an Android app writes one item for each, from one typed password. `add` refuses browsers, home screens and system apps before it reads a password. `credential add --stdin` saves a user for simulators and emulators with no person; reaching phones (`--devices any`) needs one. With no app named, its menu reads the app in front on each running simulator and emulator (one `launchctl list` or `dumpsys` each), never a phone, and `offsider.login.json`; it reads the device allow-list file, without its Keychain seal, only to decide whether to ask about phones. Its encrypted data (version 2) holds the username, the password, the apps linked to it and its settings: `devices` (`virtual`, the default, for simulators and emulators only, or `any`, which also allows phones, iPhones and iPads on the allow-list), `confirm`, `confirmAlways` and `webLogin`. A version 1 item reads as no links, no confirm, `devices virtual` and no web sign-in, and every save writes version 2.
- **Context** (tags and the `--about`, `--avoid` and `--state` notes) sits in the item's attributes, which the Keychain does not encrypt, so any process running as you can read it without a prompt. It refuses email-like text, control and bidi characters, and must never hold secrets or personal details. Agents may write the notes and later sessions read them back, so `--json` lists them as `untrusted` and the skill says to read them as data. `confirm`, `confirmAlways` and `devices` are mirrored there so `login` can ask early, but only the encrypted data decides.
- **Linking** (`credential join`): a person only. It needs a terminal on standard input, always asks which app to share with, asks Link or Cancel, then Touch ID or the login password, and refuses browsers, system apps and anything on the managed `deniedBundleIDs`. A link item for the second app id stores no password, only an index for a cheap lookup; `login` trusts a link only when the canonical item's encrypted data lists that app, which only `join` writes. Links saved by earlier versions, or planted in the index alone, are not trusted until `join` runs again; `join` then decrypts the shared app's users and, after the same prompts, writes the link into each one that lacks it. `credential remove` on a linked id unlinks it with no prompt, since it only takes access away: it removes the id from each user's encrypted links first and the index item last, so a failure part way still types nothing.
- **Loosening** a user (`--devices any`, `--no-confirm`, `--no-confirm-always`, `--web-login`) needs a terminal and Touch ID or the login password; tightening, `--confirm-always` included, needs neither.
- **The presence check.** A user saved with `--confirm` (on by default with `--devices any`), except on a test device, or with `--confirm-always`, on every device, makes `login` ask for Touch ID, an Apple Watch or the login password before it reads the password; the macOS sheet names the user, the app and the device. It uses LocalAuthentication's device-owner check inside Offsider, because Keychain items that require user presence need the data protection keychain, which a command-line tool signed with Developer ID cannot use without a provisioning profile and an app bundle. With no GUI session (plain `ssh`) it fails closed with `person_required`.
- **`login`** types a password only into the app it was saved for or a person linked, and refuses: a browser or system app in front (`app_not_allowed`); a password field inside a web view, unless both the saved user (`--web-login`, by a person) and the repository's `offsider.login.json` (`"webLogin": true`) opt in; another app coming to the front before the password or before the submit tap (`foreground_changed`, recomputed from the tree it just read); a Cloudflare Turnstile widget (`turnstile_required`); and a phone or tablet that is not allowed, or, unless it is a test device, a user without `devices any`. On an iPhone or iPad the username and password go only as key presses through the session broker, never the runner; with no broker, or a character a US keyboard cannot type, it types nothing. On an iOS simulator, a web view is recognised by a web-area role or by a password field drawn by another process; with neither signal it is treated as native. Offsider never taps Turnstile: `turnstile` only reads its state, and `login --wait-turnstile` waits for a person's tick. On a simulator, an emulator or a test device, `login` declines a save-password prompt with one tap on Not now, never Save, through the app guard; on a phone held to one app it taps nothing and asks the person. `login --fill password` or `--fill identity` types a saved user's password or email into a sign-up screen's password fields (at most two, showing bullets) or its one email field, with every gate of a sign-in, and submits nothing.
- **Typed text.** Offsider never echoes it, but it can show elsewhere. Text passed as an argument (`offsider type 'text'`) is in Offsider's own process arguments, like any argument; `--stdin` and `--file` keep it out. On Android, ordinary text goes as an `input text` command, which the device's process list shows, when neither gRPC nor the helper carries it; a password, or text for a field that may be one, never does (below). XCTest's result bundle and the iPhone runner's log may record text the runner typed (the runner refuses any field it reads as a password field); Offsider deletes both when the session stops, and whether they hold typed text has not been checked ([Not yet](#not-yet)).
- **Sign-in records** (`signins/`) hold the app, the app in front, the saved login's name, the platform, a stable device key, the time and a boot marker, never a username or password.
- **Unlock codes** (`unlock-code set`): service `com.mpalmes.offsider.unlock-code`, account the phone serial or AVD name. `set` needs a terminal; `set --stdin` still reads the code from a pipe but confirms on `/dev/tty` and with Touch ID or the password. On a phone it needs the phone to be allowed first. `wake --unlock` types the code once, as key events through the UiAutomation helper's authenticated socket, and only into a focused password field inside System UI's lock screen; without the helper it types nothing (`helper_unavailable`). It never becomes a process argument on the device. Before the first key, an `unlock/device-<id>.failed` marker is written (a write failure stops the command), holding only the outcome, the time and whether the lock was a PIN or password. An attempt with no result clears once the device is seen unlocked; a rejected code stays blocked until it is saved again, so a wrong code is never typed twice.
- **The allow-list seal**: a login Keychain item (service `com.mpalmes.offsider.devices`, account `allowed-devices`, never synchronised) holding the SHA-256 of the allow-list.
- **The guard seal**: a login Keychain item (service `com.mpalmes.offsider.guards`, account `guards`, never synchronised) holding the SHA-256 of `guards.json` and the apps it covers. Both digests sit in an attribute that reads without a prompt.

## Simulators

- Xcode's private simulator frameworks (CoreSimulator, SimulatorKit and related) load at runtime from the selected Xcode. Offsider first resolves `DEVELOPER_DIR` or `xcode-select` with `realpath`, requires `<name>.app/Contents/Developer`, and checks that the app satisfies `anchor apple`, or, for Xcode from the Mac App Store, whose app the store signs, Apple's Mac App Store signature on `com.apple.dt.Xcode` with Apple's team identifier, read from the signature because the store's certificate names no team (its main executable and `Info.plist`, about 40 ms, once per process), refusing with `xcode_unusable` otherwise; `doctor` reports it as `xcode.trust` (`Sources/OffsiderCore/Platform/DeveloperDirectoryTrust.swift`). The check proves the app's main executable and `Info.plist` are Apple's; library validation is what stops a non-Apple framework loading into the signed binary. `devicectl` and `xcodebuild` run only from a trusted Xcode too.
- Before each private Objective-C method Offsider's own code calls through a cast, it compares the method's type encoding with the one it recorded, and fails with `xcode_unusable` rather than call a changed method or one it has no record for (`Sources/OffsiderCore/Platform/PrivateAPIGuard.swift`). C functions it finds with `dlsym` and key-value reads carry no encoding, so they are not checked, and idb's frameworks, built from the pinned fork, make their own private calls unchecked. `doctor`'s `xcode.private-api` runs the same comparison ahead of time and warns when CoreDevice is newer than the last version tested.
- Simulator HID input (touches, key presses, buttons and text) goes to the simulator named with `--device`, through a broker on a per-user Unix socket under `$TMPDIR/offsider-hid-<uid>`: `offsider` started detached in its own session, one per simulator, holding the simulator's input session so later commands skip opening it, and on iOS 27 and later its automation session, so reads skip opening one too. The broker rejects connections from any other user, and from any process that does not satisfy its own code signature's designated requirement (checked once per connection; a release build accepts any Offsider of the same team and identifier, a development build only itself; `Sources/OffsiderCore/Platform/PeerCodeIdentity.swift`), before sending them anything, serves at most 32 commands at once, gives each request 2 s to arrive whole once its first byte has, passes their input to the simulator one request at a time, and refuses a request of more than 65,536 events, a coordinate that is not finite or beyond ±100,000, a pause that is not finite or is outside 0 to 3600 s, or pauses over 3600 s together. When a command goes mid-request it stops within 100 ms, and it lifts any touch, key or button a command leaves down; `touch --down` alone stays down until a later `touch --up`. It closes a command that sends nothing for the idle time while holding nothing down, and input too long for it (over 65,536 events) goes through the command's own session. It stops 60 s after the last command (`OFFSIDER_SIMULATOR_SESSION_IDLE`, at most 3600), when the simulator restarts, on `offsider session stop`, or at its next idle moment once 12 hours old, and logs only its start and why it stopped. When input fails it stops too, after input already queued finishes, and the commands still attached open sessions of their own. `OFFSIDER_SIMULATOR_SESSION=off` opens an input session for each command instead, though `touch --down` or `--up` alone still uses the broker. A command the broker closes before its handshake cannot ask who closed it, so it finds the broker among this user's `offsider` processes by its arguments (`hid-broker --udid <udid>`) and the socket it holds, checks that process's code the same way, and stops it (SIGTERM) only when it is another Offsider build's, then starts its own; a broker of this build is never stopped that way.

## Android emulators and phones

- **The helper.** A small helper, Offsider's own code built from the Java source in this repository, reads the screen through UiAutomation and can inject input. Its dex is pushed 0600 into a 0700 folder made by the shell user, `/data/local/tmp/offsider-push-<pid>`, then moved to its content-addressed name, `offsider-helper-<hash>.dex`, made 644 and the folder removed, so it is never writable by others; it stays until a newer helper replaces it. On every start the start script opens the copy once, checks the SHA-256 of what it opened against the manifest (`sha256sum`), and only on an image without `sha256sum` falls back to its size, then loads the helper from that same open file (`CLASSPATH=/proc/self/fd/3`), so a file swapped in after the check never runs. The Mac's copy is checked against the digest compiled into Offsider. The helper runs with `app_process` as the shell user, listens on a randomly named local socket, accepts one connection only from the shell or root user and only when the first message carries a random token printed only on the shell stream that started it, then stops listening. It exits when that connection or its shell closes, or after 10 s without a request (30 s for a warm helper, whose broker pings it every 2 s). While it runs it holds Android's single UiAutomation slot, and the device reports an accessibility service as enabled. When it cannot run, a temporary `uiautomator` dump under `/data/local/tmp` is read and deleted instead.
- **The warm helper.** On an emulator, and on an allowed USB phone only with `OFFSIDER_ANDROID_SESSION=on`, the helper outlives the command, so the next one skips its start and the wait for a quiet screen. A broker keeps it: `offsider` started detached in its own session, holding the helper's start shell and its one connection, so the token stays in the broker's memory and never reaches a disk. Commands reach the broker on a 0600 Unix socket in `sessions/`, which refuses other users (`getpeereid`) and any process that does not satisfy its own code signature's designated requirement, as the simulator and iPhone brokers do, serves at most 8 commands at once and passes their requests to the helper one at a time; it refuses `quit`, never sends input whose command has gone or that waited over 4 s behind another command, and gives up on the helper when a command's own timeout passes, counted from when its request arrived. It stops 60 s after the last command (`OFFSIDER_ANDROID_SESSION_IDLE`, at most 3600), on `offsider session stop`, when the helper misses its ping, or at its next idle moment once 12 hours old, and stopping it ends the helper, which frees the slot. Until then Appium, Maestro, `uiautomator`, instrumentation tests and Layout Inspector cannot connect, and apps can see an accessibility service enabled. A command that reads the screen another way (`OFFSIDER_ANDROID_TREE=uiautomator`, `OFFSIDER_ANDROID_SESSION=off`, a phone without `on`) stops Offsider's own warm helper on that device first, once no other command is using it, and removing a phone from the allow-list stops its one. Passwords and unlock codes typed through the helper pass through the broker's memory and are never logged. For an emulator with one display it also keeps, in memory only, the device states and display list a command read, which later commands reuse instead of reading them again. A command or `session stop` it closes before a byte finds it by its arguments (`android-session serve --device <serial>`) and the socket it holds, and stops it the same way, only when it is another build's. `OFFSIDER_ANDROID_SESSION=off` keeps one helper per command.
- **Typing secrets.** A password from `login`, any text typed into a focused password field without gRPC, and text from `--stdin`, `--file` or a batch step into a field whose focus cannot be read, goes through the helper as key events, never as an `input text` command that other shell-user processes could see in the process list; without the helper nothing is typed. A clipboard paste is refused for a password field and for a field whose focus cannot be read. Over gRPC, non-ASCII text is pasted through the emulator's clipboard, which is restored afterwards; whether the emulator's clipboard sharing copies a paste to the Mac's pasteboard has not been checked ([Not yet](#not-yet)).
- **gRPC.** The emulator's endpoint on loopback is authenticated with the token from the emulator's discovery file, or with a short-lived JWT: Offsider keeps the private key in memory and writes only the matching public key to the emulator's `jwks` folder, deleting it when the command ends; a key left by a killed command is removed by the next one.
- **Booting.** `offsider boot` starts the SDK's emulator with `-no-metrics`, never `-port` or `-grpc`. `--emulator-arg` accepts only an allow-list of flags that shape the device or its rendering, each value checked; flags that open a listener, connect out, read a host path or send metrics are refused, as are Offsider's own flags and `@name` tokens. `-camera-back` and `-camera-front` take only `emulated` or `none`, so an agent cannot see through the Mac's camera; an AVD's own `config.ini` can still name a webcam. Offsider never uses Google's Android CLI and never bundles adb.
- **State that persists.** `stay-awake` writes the `stay_on_while_plugged_in` global setting; `wake` sends `KEYCODE_WAKEUP` and `wm dismiss-keyguard`; `permission`, `status-bar`, `appearance`, `content-size` and `orientation` change settings that outlive the command, as does `biometric` enrolment on an emulator; `alert accept`, `deny` and `choose` leave the app's permission set (undo with `permission reset`, or on an iPhone in Settings); `airplane on` turns airplane mode on, recorded first in `airplane/`, and `session stop` and `devices remove` turn off only what Offsider turned on; and `posture` on a phone sets a `cmd device_state` override, recorded first in `postures/` with the phone's boot id and reset by `posture reset`, `session stop` and `devices remove` while it is still the one Offsider set.
- **Phones.** A USB phone is refused until a person allows it (below). An allowed phone's setters change the phone itself: `status-bar override` and `stay-awake on` say so with the undo command, `permission ... all` is refused, since it would reach SMS, the call log and location, and `permission --app` and the `app` commands must name an allowed app that is not on the deny-list; `app open` sends its link to that package alone and refuses `intent:`, `file:`, `content:`, `javascript:` and `data:` links; `biometric` is refused. Wi-Fi and TCP adb connections are refused, as is a USB device reporting an emulator's serial; when adb cannot list devices, an `emulator-N` serial is refused rather than trusted.
- **Metro reverse.** A debug build on a phone reaches Metro on the Mac through `adb reverse`, and while one is set every app on the phone can reach that port. Offsider sets one only from `rn open`, and only when: the phone is allowed over USB and a person chose that port under Metro in `devices add` (None is the default, and agents cannot add a port); the port is 1024 to 65535 and not adb's server or an emulator's console, adb or gRPC port; Metro answers `packager-status:running` on 127.0.0.1 at it; and the process that accepts a connection there runs as this user, read from this user's own processes' sockets. It maps the same port on both sides (`tcp:<port> tcp:<port>`) with `norebind`, so it never replaces a reverse someone else set. Each one is recorded first with the phone's adb connection number, in the private `reverses/` folder, and dropped again only when adb refuses, as after a timeout it may be set. `session stop` and `devices remove` take off only the recorded ones still mapped that way, never another reverse, and say what they could not remove with the command that retries; a reverse ends anyway when the phone is unplugged or the adb server stops. `rn open` also runs the owner check before it uses a reverse already there, refuses one it set once a person withdraws its port, and `devices add` takes off the reverses for ports it drops. Emulators reach Metro at 10.0.2.2 and never get one.
- **The app in front.** Outside a test device, the deny-list (`Sources/OffsiderCore/Login/SystemAppDenyList.swift`) holds named browsers, launchers and system apps (Settings, System UI, Chrome and its channels, Firefox, Samsung Internet, Brave, Edge, Opera, DuckDuckGo, Samsung's system apps, Gmail, Outlook, Messages, Play Store, Google Play services, Photos, Contacts, the dialer, the permission controller, the package installer, Wallet, WhatsApp, Signal, Telegram, Slack, Teams, the named password managers (1Password, Bitwarden, LastPass, Dashlane, Keeper, Proton Pass, Enpass) and authenticator apps, and Find My Device), matched by exact id or by prefix, plus any managed `deniedBundleIDs`. It is a list of named common apps, not a category: add the rest with `deniedBundleIDs`. With such an app in front, an app outside the allowance, or an app Offsider cannot name: a screen read, a screenshot, a video frame (read at most once a second) and every input step are refused (`app_not_allowed`), the app in front being read again before each input step and before a capture that follows input. Buttons are not checked, so a phone can always be sent home, and a finger already down is not checked again for its move or lift. A screen read also checks the active window, so the notification shade or quick settings open over the app are refused; a screenshot or coordinate input without a tree read relies on the resumed activity alone, which the shade does not change.
- **Notifications on a phone.** `notifications` reads one allowed app at a time and picks its records on the device: on Android 11 and later by key (`cmd notification list`, keeping keys whose package field is the app's, then `get` for each), so another app's notification text never reaches the Mac; on Android 8 to 10 by a shell filter over `dumpsys notification --noredact` that keeps the app's records in the active list. That filter works line by line, and notification text can hold line breaks, so a notification whose text imitates a record header for the allowed app can carry the rest of its own record past it. Values are redacted as screen text is.
- **Logs on a phone.** `logs` reads one allowed app at a time (`--app`, else the single pin, else `offsider.login.json`'s package when allowed). The whole device's log (`--all`, `--process`, or no app) needs the allowance "Any app and all logs", which only a person chooses, or a test device.

## Physical devices: the allow-list

- Every command that names a physical iPhone, iPad or Android phone checks the allow-list first and refuses with `device_not_allowed` (exit 7), sending the device nothing: an iPhone is refused before any `devicectl` call, a phone after reading only the adb server's own device list. The exception is clean-up: `session stop`, `session stop --clean` and `devices remove` can still reach a device this Mac set up before, only to undo what Offsider left there (the runner apps, Metro reverses, posture and airplane overrides). `devices` hides such rows unless `--physical` is passed. A physical device must be named with `--device` on each command; `OFFSIDER_DEVICE` never names one. Each command that drives an allowed device prints one line to stderr naming it, its expiry and how to withdraw it.
- `offsider devices add` is the only way onto the list. It needs a terminal on standard input (without one it exits 1 with `person_required`), asks a person whatever flags and this Mac cannot settle, shows a summary, then asks for Touch ID or the login password, whose box names the device, a whole-device reach and registering it with a team. `devices add --plan` lists rows and teams only, so an agent can hand over the command but not run it. The terminal is a speed bump, as an agent driving a pseudo-terminal can pass it; Touch ID is the gate. Building those menus adds two local reads. The team menu lists the code-signing identities in the login Keychain: identities only, never private keys, and with no prompt. The app menu sends one installed-apps query to the chosen device (and, on an Android phone, one read of the app in front), only after the person picked it in the menu and before Touch ID: a deliberate trade-off, so an agent driving a pseudo-terminal can list a phone's apps without allowing it. A failed query falls back to typing an app id. Deny-listed apps and apps outside a managed ceiling are not offered. One app is preselected (`offsider.login.json`'s app when installed, else on Android the app in front); "Any app" is never preselected and says it includes banking and messages, and on Android "Any app and all logs" (stored as `*`) also allows whole-device logs. A device passed with `--device` gets the same summary, naming the device by its model, and the same Touch ID.
- Entries expire: 7 days for one app and 12 hours for any app by default, at most 30 days, or `never`; a test device lasts until removed. An entry can pin the apps Offsider may drive (with none, each command drives only the app it names, on every platform), for an iPhone or iPad can record the team that signs its runner and the runner's bundle id prefix (`--runner-prefix`), and for an Android phone the Metro ports `rn open` may reverse (the Metro step offers None first and chosen, and the Touch ID prompt names any port chosen). Parsing is strict: a hand edit refuses the whole list, and an entry a newer Offsider wrote refuses only that device (`newer_entry`) until Offsider is updated. `remove` needs no terminal, and on an iPhone or iPad also stops its runner and session broker, deletes `runner.log`, and offers to uninstall the runner (or prints the command off a terminal).
- **Test devices.** A person can mark a device a test device in `devices add` (`--test-device`), their word that it holds nothing personal; nothing checks it. On a test device Offsider lifts these limits: the browser and system-app deny-list for driving (`login` and `credential` still refuse them), the front-app check, `login`'s need for `--devices any` and its `--confirm` Touch ID, Touch ID for `wake --unlock`, and the per-app log limit. Typing a passcode, pairing, tapping Trust, Wi-Fi and registering the device with a team stay refused, and an agent's tap can reach a system prompt there. `alert` reads and answers an app's permission prompt only on simulators, emulators and test devices, never on a phone in personal use, and holds `accept` and `choose` to the app's guard rules. On a Mac with any forced managed key, a test device is a plain Any app allowance unless `allowTestDevices` is forced true and neither app list is forced ([docs/device-access.md](docs/device-access.md#test-devices)).
- The list is sealed: `add` and `remove` store the file's SHA-256 in the login Keychain, and an edit made any other way, or a missing seal beside a non-empty file, refuses every device until a person runs `add` again (`Sources/Offsider/Utilities/DeviceAllowListSeal.swift`). A seal that cannot be read, as in a locked Keychain, refuses every device too, as `seal_unreadable` rather than a changed list, and `add` and `remove` refuse while it cannot be read, rather than drop every other entry; `guard approve` does the same for the guard seal. This turns a quiet file edit into a deliberate Keychain write; a hostile process running as the same user can still delete and re-add the item.
- Managed preferences set a ceiling above the list ([Managed preferences](#managed-preferences)). Both the ceiling and the list must allow a device; only the ceiling is beyond a process running as the user.
- The list, the seal and managed preferences are read only by commands that name or list a physical device (except `deniedBundleIDs`, which `login` and `credential` read on every device), once per process, and never cached on disk; the iPhone session broker reads them again every 30 s.

## iPhones and iPads

- **Connection.** USB only: only a wired transport passes, and before each input batch usbmuxd must still list the device on USB. Offsider never pairs a device, never accepts a prompt on it by itself and never types a passcode; on a test device, an agent's tap can reach a prompt.
- **One app.** Outside a test device, each command drives one app: `--app`, else `offsider.login.json`'s `bundleId`, else the allowance's only pinned app. It must not be a browser or system app (by id or prefix, compared without case, Gmail, Outlook, WhatsApp, Signal, Telegram, Slack, Teams, the named password managers, authenticators and Find My included, plus any managed `deniedBundleIDs`) and must be within the allowance's apps and any managed `allowedBundleIDs`. Before each screenshot, broker or video frame, each input batch and each detached touch, the runner checks with XCTest's own active-app lookup that the app is in front (on Xcode 27.1 and later, its accessibility client's active apps; only with neither does it fall back to the app's own foreground state, which may miss a system alert or Control Center over the app and passes for an app sharing the screen in Split View or Stage Manager), and the command stops with `app_not_allowed` before reading or touching the screen otherwise. A confirmation is reused for up to 2 s within one command only while no input is sent: any input clears it, so a capture after a tap checks again.
- **Android pins.** An Android phone's allowance can pin apps too (the app step of `devices add`, or `--app <package>`), narrowed by any managed `allowedBundleIDs`: with a non-empty set, the checks above refuse another app in front with `app_not_allowed`, naming the allow command, or saying the managed ceiling cannot be overridden. With no pins, each command drives only the app it names (`--app`, else `offsider.login.json`'s `package`) and refuses with neither.
- **The runner.** The accessibility tree comes from a small XCUITest runner app built from source bundled with Offsider into `~/Library/Caches/offsider/runner/` (0700). Each source file copied into the cache is checked against the digests compiled into Offsider.
- **Its team.** It is signed only by the team a person recorded in `devices add`, by picking it from the menu of the login Keychain's signing identities or typing it (`--team` in scripts), or, when the allowance names none, the team in `OFFSIDER_IOS_TEAM_ID`; a variable naming another team than the allowance's is refused. Xcode's signed-in team is never picked silently, only by a person in that menu. Its bundle ids are `<prefix>.runner` and `<prefix>.runner.uitests`, with the prefix the allowance saved (sealed with it under Touch ID), else `OFFSIDER_IOS_RUNNER_PREFIX` (default `com.mpalmes.offsider`, validated; one naming another prefix than the allowance's exits 64); the first build under any other prefix creates App IDs in the team, so only `offsider runner build --device <UDID>`, confirmed by a person at a terminal with Touch ID or the login password, may do it, and the approved prefix is remembered in `approved-prefixes` in the runner cache, its SHA-256 sealed in a login Keychain item that reads with no prompt: a file that does not match the seal, such as one another program wrote, counts as no approval, so `runner build` asks the person again. A build registers the device with the team only when a person does it: `devices add` with a team chosen, whose Touch ID box says so, or `offsider runner build --device <UDID> --register-device`, which needs a terminal on standard input and output and Touch ID or the login password. Builds still pass `-allowProvisioningUpdates`, so Xcode creates or renews the runner's App IDs and profiles in that team without asking.
- **Its products.** After a build, `products.json` (0600) records the device, team, prefix and the SHA-256 of each product. Before each session starts, the products are hashed again, and the host app, the runner app and the `.xctest` bundle must satisfy `anchor apple generic and certificate leaf[subject.OU] = "<team>"` with their resources validated; otherwise the build is deleted and rebuilt once, then refused.
- **Running it.** It is launched detached with `xcodebuild test-without-building -quiet`, listens only on the device's loopback with a token per session, and is reached only through usbmuxd (`/var/run/usbmuxd`). Offsider's session record (pid, port and token, 0600), `runner.log` and result bundles live under `ios-devices/<UDID>/`; the token is never printed, and result bundles are deleted when a session stops or an exited one is forgotten.
- **The session broker** (Xcode 27) holds the device's CoreDevice screen stream, its UniversalHID touchscreen and keyboard and its hardware button socket. It listens on a 0600 Unix socket in `sessions/` and refuses other users and any process that does not satisfy its own code signature's designated requirement, as the HID broker does. Every 30 s it reads the device's allowance again (the file, its seal and managed policy) and asks usbmuxd whether the device is still on USB, and when either fails it ends the stream, releases any held touch, key or button and stops. It serves at most 8 clients at once, drops a client that sends no first request within 10 s, is then silent for the idle timeout or takes more than 10 s to send a started request, refuses a request with more than 4,096 steps, a wait that is not finite or is outside 0 to 30 s, or waits over 60 s together, caps swipes at 1,000 steps and 30 s, refuses frame sizes over 16,384 pixels a side, and presses only the home, lock, side and Siri button usages. Its screen stream reaches the Mac only through CoreDevice's USB tunnel ([Network](#network)), and the device shows its screen-sharing indicator while it runs.
- **Lifetime.** The runner and the broker stop after `OFFSIDER_IOS_RUNNER_IDLE` and `OFFSIDER_IOS_SESSION_IDLE` seconds without a request (default 300, at most 3600). A runner session older than 12 hours is restarted on its next use, and a broker older than 12 hours stops at its next idle moment.
- **The developer disk image.** Any device command's wake step asks CoreDevice for `ddiServices`, which mounts a missing developer disk image, and `doctor --fix` mounts one too; both happen only on an allowed device named with `--device`.
- **What stays.** `session stop` stops the broker and the runner, clears the screen-sharing indicator and deletes `runner.log`; the runner apps stay installed and the cache stays. `session stop --clean` (or `runner stop --clean`), which also works once the device's allowance has expired or been removed when this Mac holds its runner build or session record, also uninstalls `<prefix>.runner.uitests.xctrunner` and `<prefix>.runner`, and deletes this device's runner builds, `runner.log` and the broker's log. What only the Apple developer site (Certificates, Identifiers & Profiles) removes stays in your team: the runner's provisioning profile, its App IDs and the device's registration.

## App guard

- **Rules.** `offsider.guard.json` in an app's repository names the controls an agent asks a person about (`ask`) or never taps (`never`). Every tap, drag, swipe, slider and Return is judged on the control it would land on, read from the tree and the screen's text, before anything is sent; a `never` control is refused with `guarded_control` (`Sources/OffsiderCore/Guard/`, `Sources/Offsider/Utilities/AppGuard.swift`).
- **Ask.** An `ask` control waits for Touch ID or the login password at the Mac, and only on a simulator, an emulator or a test device that Offsider signed in with a saved login (one the rules name, when they name any); anywhere else the tap is the person's and nothing is sent.
- **Approval.** A person approves an app's rules once with `guard approve` at a terminal with Touch ID or the login password (or in `devices add`). After that an agent's edit of the repository file can tighten the rules but never loosen them. Approvals live in `~/.config/offsider/guards.json`, sealed in the login Keychain ([Saved secrets](#saved-secrets)), and a broken seal stops input to the apps it covers.

## Managed preferences

An administrator sets a ceiling with a configuration profile in the domain `com.mpalmes.offsider` ([Managed Macs](docs/mdm.md) has the keys, a sample profile and how to verify it).

- **Forced only.** Offsider honours a key only while macOS reports it forced (`CFPreferencesAppValueIsForced`), so `defaults write` changes nothing (`Sources/OffsiderCore/Policy/ManagedDevicePolicy.swift`).
- **Device keys:** `allowPhysicalDevices`, `allowedDeviceIDs`, `allowedBundleIDs`, `deniedBundleIDs` (an entry ending in `.` is a prefix; it extends the deny-list for `login` and `credential` on every platform and for every physical device) and `allowTestDevices`. Any forced key turns test devices into plain Any app allowances unless `allowTestDevices` is forced true and neither app list nor `requirePinnedApps` is forced.
- **Ceilings on what may be loosened:** `forceMasks` (no mask or redaction can be dropped, by a person or an agent), `maxAllowanceDays`, `allowSavedLogins`, `allowFileInput` (`--allow-path`), `allowMetroReverse`, `allowRunnerRegistration` (also drops `-allowProvisioningUpdates` from the runner build), `allowedTeamIDs`, `requirePinnedApps`, `allowUnlockCodes` and `allowPhonePermissionChanges`. Each is read only by the flag or command it governs (`Sources/OffsiderCore/Policy/ManagedCeilings.swift`), so a simulator or emulator command that loosens nothing reads no managed key, and each refuses with `managed_policy`, naming the key, before anything is captured, saved or sent.
- **Both must allow.** The ceiling and each person's allow-list must both say yes before a physical device is driven (`Sources/OffsiderCore/Policy/PhysicalDevicePolicy.swift`).
- **Fail closed.** A forced key of the wrong type refuses every physical device, and so does a forced key this build does not know; `devices status` names the key. A ceiling of the wrong type also holds at its strictest value on every device. Keys starting `Payload`, which some MDM tools leave beside the settings, are ignored. A malformed `deniedBundleIDs` also refuses `login` and `credential` on simulators and emulators.

## Release integrity

- Releases are built by `.github/workflows/release.yml` in separate jobs, each on a fresh GitHub-hosted runner (the v0.17.0 run's jobs report the runner group `GitHub Actions`). The build job holds no secrets: it checks the tag's signature against `main`'s `.github/allowed_signers` and that the tag is on `main`, builds the binary, the idb frameworks and the runner check, and packs an unsigned payload with its SHA-256. A signing job in the protected `release` environment checks out the tag commit, verifies the payload's digest, lists it before unpacking (only plain files, folders and links inside the tree, no absolute path, `..`, hard link or device, at most 1 GiB), signs and notarises it, and never builds or runs it; the signing keychain and the notary key are removed as soon as each is used. A verify job with no environment lists the signed archive the same way, unpacks it, verifies the signatures and notarisation, runs the signed binary through commands that load CoreSimulator and SimulatorKit and fails on any library validation rejection in the system log, and runs the Homebrew gate. Only then is the release published, immutable, with its `SHA256SUMS` and a GitHub build provenance attestation.
- On a `v*` tag the build job stops before building unless line 1 of this file names that version, and `scripts/release.sh tag` will not make the tag without it. From 0.18.0 the build job also writes `build-info.txt` (runner, Xcode, Swift, the idb pin, the helper's digest, the commit and the workflow ref), the CycloneDX 1.6 SBOM `offsider-<version>.cdx.json` (`scripts/sbom.sh`) and a copy of this file, and the publish job refuses them unless they match what the build job saw. The release attaches all three and the provenance bundle (`offsider-<version>-arm64.tar.gz.intoto.jsonl`), lists them in `SHA256SUMS` and attests them; the SBOM is also attested on the tarball.
- The `release` environment's one required reviewer is the maintainer, who can approve their own run. Tags are signed with an SSH key listed in `allowed_signers`, which is not yet hardware-backed.
- Release binaries are signed with a Developer ID certificate (its team is in [Verify an install](#verify-an-install)), use the hardened runtime and are notarised by Apple. Their entitlements, in [entitlements.plist](entitlements.plist), are empty: library validation is on, so the binary loads only frameworks signed by the same team or by Apple. Ad-hoc builds for local rehearsals use [entitlements-adhoc.plist](entitlements-adhoc.plist), which disables library validation because an ad-hoc signature has no team; `scripts/release.sh` refuses to sign a release with a file that disables it.
- The SHA-256 of every file in Offsider's resource bundle (the Android helper's dex and manifest, the skill, the guide topics and the runner's source) is compiled into the binary at build time. A file that differs is refused with `install_damaged` when it is read (`Sources/Offsider/Platform/BundleIntegrity.swift`). A replaced binary loses its Developer ID signature, but nothing refuses to run it: a Homebrew install carries no quarantine flag, so Gatekeeper does not look again, and only macOS's Keychain access check and the brokers' signature check (a replaced binary is not the build a running broker serves) notice. `codesign --verify` ([Verify an install](#verify-an-install)) is what catches it.
- The Homebrew formula is updated only through a pull request on the tap, opened by a GitHub App with access to that repository alone, and merged by auto-merge only after the tap's own checks pass. Those checks render the formula with `render_formula` from the tagged release's `scripts/release.sh` and fail on any byte of difference, a pull request touching other files, a URL other than the release's own, a prerelease or a downgrade, then install it after checking its SHA-256 and verifying its attestation with `--source-ref` and `--deny-self-hosted-runners`.
- A pull request's head commit must be signed by a key in the base branch's `allowed_signers`, whatever it changes (the `Protected paths signed` check, which runs the base branch's copy of its workflow), so an account taken over without that key can merge nothing.
- The idb frameworks are built from the [michael-palmes/idb](https://github.com/michael-palmes/idb) fork of facebook/idb (with Xcode 27 changes) at a pinned commit that `scripts/build.sh` verifies before building, and Swift package versions are resolved strictly from `Package.resolved`. The Android helper's dex is rebuilt from its source with a pinned toolchain and compared with the committed copy in CI.
- One maintainer holds admin rights on the repository. An admin account takeover could still change its rules; a hardware security key on the account is the backstop.

## Verify an install

A Homebrew install:

```bash
OFFSIDER=$(readlink -f "$(command -v offsider)")
codesign --verify --strict --verbose=2 "$OFFSIDER"      # valid on disk, unchanged
codesign --verify -R='anchor apple generic and certificate leaf[subject.OU] = "Q4B8N8ZKA2"' "$OFFSIDER"   # Offsider's release team
spctl --assess --type install --verbose=2 "$OFFSIDER"   # source=Notarized Developer ID
codesign -d --entitlements - "$OFFSIDER"                # empty, so library validation stays on
offsider doctor                                         # install.bundle: bundled files match the build
```

A downloaded release, at the latest tag:

```bash
VERSION=$(gh release view --repo michael-palmes/offsider --json tagName -q .tagName | sed 's/^v//')
gh release download "v$VERSION" --repo michael-palmes/offsider \
  --pattern "offsider-$VERSION-arm64.tar.gz" --pattern SHA256SUMS
shasum -a 256 -c SHA256SUMS --ignore-missing
gh attestation verify "offsider-$VERSION-arm64.tar.gz" --repo michael-palmes/offsider \
  --signer-workflow michael-palmes/offsider/.github/workflows/release.yml \
  --source-ref "refs/tags/v$VERSION" --deny-self-hosted-runners
```

From 0.18.0, each release attaches its provenance bundle, so you can verify the tarball without asking GitHub for the attestation (add `--custom-trusted-root` with a file from `gh attestation trusted-root` to verify with no network at all), and check the SBOM attested on it:

```bash
gh release download "v$VERSION" --repo michael-palmes/offsider \
  --pattern "offsider-$VERSION-arm64.tar.gz.intoto.jsonl" --pattern "offsider-$VERSION.cdx.json"
gh attestation verify "offsider-$VERSION-arm64.tar.gz" --bundle "offsider-$VERSION-arm64.tar.gz.intoto.jsonl" \
  --repo michael-palmes/offsider --signer-workflow michael-palmes/offsider/.github/workflows/release.yml \
  --source-ref "refs/tags/v$VERSION" --deny-self-hosted-runners
gh attestation verify "offsider-$VERSION-arm64.tar.gz" --repo michael-palmes/offsider \
  --signer-workflow michael-palmes/offsider/.github/workflows/release.yml \
  --source-ref "refs/tags/v$VERSION" --deny-self-hosted-runners --predicate-type https://cyclonedx.org/bom
```

The SBOM lists the Swift packages, the idb fork with its upstream, the bundled frameworks, the Android helper, and the Xcode and macOS frameworks loaded at run time and never shipped.

[Install](docs/install.md#verified-tarball) unpacks it and puts it on your `PATH`.

## Build hardening

- `OffsiderCore`, `OffsiderAndroid` and `OffsiderIOSDevice`, the pure logic and the device backends, are compiled with Swift's strict memory safety checking, so each unsafe pointer, C string and C call is marked where it happens, and a unit test fails if a target loses the setting. The command target, which calls idb's frameworks, is not.
- CI runs the unit tests under AddressSanitizer after each merge to main and weekly, and under ThreadSanitizer weekly, and property tests feed the parsers seeded random and malformed input on every `swift test`.
- A weekly job fuzzes the parsers for device, daemon and file bytes (adb, the helper's frames, usbmux, screenshots, uiautomator dumps, the media stream answer, the tree cache, the allow-list, the mask file, JSON and the log redactor) under AddressSanitizer. It is a mutation fuzzer, not coverage guided, since Xcode's toolchain ships no libFuzzer runtime.

## Process

- **Every pull request** to `main` must pass the required checks: Lint (shellcheck and actionlint), Leak gate (private strings), the Android helper rebuild and compare, the React Native playground typecheck, `Protected paths signed`, and `CI passed`, which also needs the unit tests and an ad-hoc release build and rehearsal on any change beyond docs (`.github/workflows/ci.yml`, `scripts/ci-gate.sh`). Commits on `main` must be signed. There is one maintainer, so no second person approves a merge.
- **Signed heads.** A pull request's head commit must be signed by a key in the base branch's `allowed_signers` (`.github/workflows/signers.yml`).
- **An AI review before each pull request.** The maintainer runs `/code-review high` (Claude Code's review) on the branch and works through each finding for speed, security, privacy and an easy secure path, writing a reason for any left in the pull request (`CLAUDE.md`, "Pull requests"). It is not a human review.
- **After each merge and weekly,** the unit tests run under AddressSanitizer, and **weekly** under ThreadSanitizer (one test of a signal handler's timing left out, as TSan defers handlers); a failure of either opens an issue on `main` (`ci.yml`, "Unit tests (AddressSanitizer)" and "Unit tests (ThreadSanitizer)").
- **Weekly fuzzing** of the parsers for device, daemon and file bytes, under AddressSanitizer (`.github/workflows/fuzz.yml`).
- **Workflow hygiene.** Every workflow starts from `permissions: {}` or `contents: read`, pins each action to a full commit SHA, and checks out with `persist-credentials: false`; Dependabot proposes action and Swift package updates weekly after a 7-day cooldown, the Swift ones through a copy of the manifest's remote requirements in `swiftpm-watch/`, which a unit test keeps in step with the root's (`.github/dependabot.yml`, `Tests/SwiftPMWatchTests.swift`).
- **Scans.** OpenSSF Scorecard runs weekly and on each push to `main`, with its results published (`.github/workflows/scorecard.yml`); CodeQL scans the workflows, the Java Android helper and the TypeScript test fixture on pull requests, pushes to `main` and weekly (`codeql.yml`); dependency review runs on every pull request (`dependency-review.yml`). CodeQL does not scan the Swift code, because it cannot analyse Swift 6.4 yet.
- **Releases** come only from a signed tag on `main`, through the jobs in [Release integrity](#release-integrity), and the Homebrew tap updates only through its own checked pull request.
- **Reviews.** In October 2026 a read-only security review of the code produced the change list that 0.12.0 to 0.14.0 shipped. There has been no third-party audit.

## Known limits

Accepted by design; each links its section.

- A hostile process running as you is out of scope: the allow-list seal and the terminal check raise the bar, and Touch ID is the gate ([Not a security issue](#not-a-security-issue)).
- Masks cover what the accessibility tree describes; web views, canvases and images can still show ([What reaches your agent](#what-reaches-your-agent)).
- Video checks for a password field once, before the first frame ([What reaches your agent](#what-reaches-your-agent)).
- Redaction works by pattern, so a secret in another shape still shows ([What reaches your agent](#what-reaches-your-agent)).
- Saved-login tags and notes sit in unencrypted Keychain attributes ([Saved secrets](#saved-secrets)).
- Text passed as an argument is in Offsider's process arguments ([Saved secrets](#saved-secrets)).
- `devices add` lists a phone's apps before Touch ID ([Physical devices: the allow-list](#physical-devices-the-allow-list)).
- The deny-list names common apps; other messaging, banking and password manager apps need `deniedBundleIDs` ([Android emulators and phones](#android-emulators-and-phones)).
- A test device is a person's word that it holds nothing personal; nothing checks it ([Physical devices: the allow-list](#physical-devices-the-allow-list)).
- A replaced binary still runs: a Homebrew install carries no quarantine flag ([Release integrity](#release-integrity)).
- Builds pass `-allowProvisioningUpdates`, so Xcode creates or renews the runner's App IDs and profiles in your team without asking ([iPhones and iPads](#iphones-and-ipads)).
- On Android 8 to 10, the notification filter works line by line, so a crafted notification can carry text past it ([Android emulators and phones](#android-emulators-and-phones)).
- idb's frameworks make their own private calls, unchecked by Offsider's type encodings ([Simulators](#simulators)).
- The app guard judges what the tree and the screen's text show; typed text and hardware buttons are not checked against it ([App guard](#app-guard)).
