# Physical iPhones and iPads

- Offsider drives an iPhone or iPad connected over USB, only after a person runs `offsider devices add`, chooses it and pins the app, or calls it a [test device](device-access.md#test-devices) ([Physical devices](device-access.md)), and only when you pass its UDID to `--device`; nothing else ever chooses one. Only a wired connection passes: a device on Wi-Fi, a network or an unknown transport is refused with `device_not_wired` (exit 7) and a hint to connect its cable, and before each input batch usbmuxd must still list it on USB.
- The device can run iOS or iPadOS 26 or 27, and the host must be macOS 26.7 or later, or macOS 27, on Apple silicon. HID input needs Xcode 27's developer disk image on the device, which Xcode 27 mounts.
- Prepare the device once: connect the cable, unlock it and tap Trust, turn on Developer Mode (Settings > Privacy & Security > Developer Mode, then restart it), and for input turn on Settings > Developer > UI Automation. Until then `devices` shows it as `Untrusted`, `Developer Mode off` or `Preparing` (while Xcode prepares it for development) with a hint on stderr. Keep it unlocked while Offsider drives it: a locked device refuses input with `device_locked` (exit 7). `offsider wake` clears a lock screen with no passcode; otherwise unlock it by hand, as Offsider never types an iPhone passcode.
- `devices` reads iPhones and iPads from `xcrun devicectl list devices`, with `kind` `physical` and `connection` `usb` or `network`. `doctor --device <UDID>` runs the [`ios-device.*` checks](troubleshooting.md#iphones-and-ipads) on an allowed device; `--fix` only mounts the developer disk image.

What works depends on the host's Xcode:

| | Xcode 27, broker | Xcode 27, no broker | Xcode 26 |
| --- | --- | --- | --- |
| `devices`, `doctor`, `appearance`, `content-size`, `orientation` | yes | yes | yes |
| `screenshot` | stream | `devicectl` | `devicectl` |
| `describe-ui`, `wait`, `assert` (runner) | yes | yes | yes |
| Element and coordinate `tap`, `swipe`, `button home` | broker | runner | runner |
| `sleep`, `wake` | runner | runner | runner |
| Plain ASCII `type` | broker | runner | `xcode_too_old` |
| Non-ASCII `type`, `type --replace` | runner | runner | runner |
| `key`, `key-sequence`, `key-combo`, `touch`, `gesture`, `drag`, the other buttons | broker | refused | `xcode_too_old` |

`xcode_too_old` exits 9. Its hint selects an installed Xcode 27 and runs its first launch, which updates CoreDevice, or says to install Xcode 27.

## Session broker

- On an Xcode 27 host (CoreDevice 636 or later), screenshots and input go through a session broker, one per device. The first command that needs it starts it in the background. It holds the device's CoreDevice screen stream, its UniversalHID service (touchscreen and keyboard) and its hardware button socket, so later commands skip that setup. Taps, touches, swipes, gestures, drags, keys and US keyboard text are sent as UniversalHID reports, and the `home`, `lock`, `side-button` and `siri` buttons as button events. A plain `lock` or `side-button` press holds for 0.34 s: iOS opens Siri from 0.40 s, and some devices ignore a press under 0.29 s. `apple-pay` is refused; press `side-button` twice instead. `app-switch` is refused too.
- Measured on a physical iPad over USB with Xcode 27, with the broker running: `tap` 132 to 148 ms, `type` 69 to 84 ms, `button home` 151 to 164 ms, a 0.3 s `swipe` about 370 ms and `screenshot` about 230 ms. The first command after the broker has stopped pays about 3 s to start it and its stream.
- The broker stops after `OFFSIDER_IOS_SESSION_IDLE` seconds without a command (default 300, at most 3600), at its next idle moment once 12 hours old, when the device goes, within 30 s of the device's allowance expiring or being removed, or on `offsider session stop`. It serves only the Offsider build it runs from (checked by code signature), so after an upgrade or rebuild the next command replaces it. It serves at most 8 commands at once, and refuses a request with more than 4,096 steps or waits over 60 s together. While it runs, the device shows its screen-sharing indicator; stopping the broker ends the stream and clears it. `offsider session status` lists each device's broker and runner without starting either, and `session stop` stops both (`--device`, `--json`); `runner status` and `runner stop` still cover the runner alone. Run `offsider session stop --device <UDID>` when you are done with a device.
- The broker needs a logged-in desktop session on the Mac: run Offsider from a terminal there, not over plain `ssh`. Without one, screenshots fall back to `devicectl device capture screenshot` (about 2.3 s each, with a one-line notice) and input falls back to the runner, as the table shows. While the Mac's display sleeps the stream cannot open either, so keep it awake for a run (`caffeinate -d` in a terminal); the broker opens the stream again once it wakes. Both paths give the panel's own size, and `screenshot --json` says which took each shot (`capture`: `stream` or `devicectl`). A `devicectl` shot draws a staged status bar (9:41, full signal), so check the status bar only on a `stream` shot.

## Runner

- The accessibility tree comes from a small XCUITest runner app. The first command that reads the screen builds it from source bundled with Offsider, with `xcodebuild` (about a minute, with a line on stderr), into `~/Library/Caches/offsider/runner/`; the build is reused until the source, Xcode, team or prefix changes. It is signed with the team a person chose for the device from `devices add`'s Keychain team menu (or `--team <id>`), or, when the allowance names none, the team in `OFFSIDER_IOS_TEAM_ID` (10 letters and digits); a variable naming another team than the allowance's exits 64. Offsider never picks the team Xcode is signed in to, and with neither, commands exit 9 with `team_missing`. `OFFSIDER_IOS_RUNNER_PREFIX` sets the runner's bundle id prefix (default `com.mpalmes.offsider`; the apps are `<prefix>.runner` and `<prefix>.runner.uitests`; a reverse-DNS name of at most 100 characters, else exit 64). The first device build under any other prefix creates App IDs in your team, so a person runs `offsider runner build --device <UDID>` once in their own terminal and confirms with Touch ID or the login password; other commands exit 1 `person_required` until then. A failed build exits 1 with `runner_build_failed` and names its log.
- Offsider never registers a device with your team unasked: `devices add` does it under the Touch ID that names it. When a later build fails because the device is not registered, the hint is `offsider runner build --device <UDID> --register-device`, which needs a terminal and Touch ID or the login password, and lets Xcode add the device to the team; `runner build` without it builds and checks the runner (`--json`).
- The runner's source is checked file by file against digests compiled into Offsider when copied into the cache. After a build, `products.json` (0600) records the device, team, prefix and a SHA-256 per product; before each session starts, the products are hashed again and must be signed by that team, else the build is deleted and rebuilt once, then refused.
- The runner is launched detached with `xcodebuild test-without-building` and listens only on the device's loopback, with a token per session. Offsider reaches it through usbmuxd (`/var/run/usbmuxd`), which connects USB devices only. When usbmuxd does not list the device on USB, a command that needs the runner exits 9 with `usbmux_unavailable` at once, or 10 s after usbmuxd drops the device while the runner starts, instead of waiting out the runner's 150 s start. Likewise, when `xcodebuild` reports that it is waiting for the device to be unlocked, the command exits 7 with `device_locked` at once, and an `xcodebuild` that exits early fails at once with `runner_unavailable` and the end of its log. When it says the Developer App Certificate is not trusted, the command exits 7 with `certificate_not_trusted` at once: trust it on the device in Settings > General > VPN & Device Management.
- A system prompt can hold an app: one reading the pasteboard waits for iOS's Allow Paste answer, and a read of it would hold the runner for about 20 s. So the runner looks for an alert or sheet first, and a read naming an app under one (`describe-ui`, `wait`, `assert`, or a tap by `--id` or `--label`, which reads first) exits 7 `system_prompt_in_front` at once, quoting the prompt, with nothing read or sent and the runner free for the next command. On a device that is not a test device, every input checks the app in front first and exits 7 the same way, and a person answers the prompt on the device. On a [test device](device-access.md#test-devices) the error names the commands instead, as a read with no `--app` reads the prompt itself: `offsider describe-ui --summary --device <UDID>`, then `offsider tap --label <button> --device <UDID>`. There a tap by coordinates, a swipe or keys go straight to the session broker with no prompt or front-app check, for speed, so they reach the prompt, not the app.
- A prompt that rises just after a read begins can still hold that read until it times out with `runner_unavailable`, and the next read gets through as it ends. A read that waited 14 s behind it, or input 4 s, is dropped, not run late, so retries cannot pile up behind a stuck app.
- The runner keeps running so later commands answer quickly, and stops after `OFFSIDER_IOS_RUNNER_IDLE` seconds without a request (default 300, at most 3600); a session older than 12 hours is restarted on its next use. `offsider runner status` lists sessions and `offsider runner stop` stops them (`--device`, `--json`); the token is never printed, and result bundles and `runner.log` are deleted when a session stops. At a terminal, `runner status` and `session status` show a person a 🔌 header with counts and a row per session, `runner build` a spinner and then a ✅ receipt with the build's folder, and `stop` a receipt; `--clean` adds a note on what only Apple's developer site removes.
- `session stop --device <UDID> --clean` (or `runner stop --clean`), which also works once the device's allowance has expired or been removed, uninstalls `<prefix>.runner.uitests.xctrunner` and `<prefix>.runner` from the device and deletes this device's runner builds, `runner.log` and the broker's log. It then prints what only the Apple developer site (Certificates, Identifiers & Profiles) removes: the runner's provisioning profile, its App IDs and the device's registration in your team.
- A device is driven inside one app. Every command that reads or drives its screen takes `--app <bundle-id>` on a device (`screenshot`, `record-video`, `stream-video`, `describe-ui`, `tap`, `type`, `swipe`, `drag`, `gesture`, `touch`, `slider`, `key`, `key-sequence`, `key-combo`, `button`, `wait`, `assert`, `turnstile`, `rn devmenu`, `rn tools off`, `rn logbox` and `batch`, and its steps); simulators and emulators ignore it. Without it, Offsider uses `offsider.login.json`'s `bundleId`, else the one app the allowance pins, and with none of them exits 64. The pin holds for that command only. The app must not be a browser or system app (Safari, Chrome, Firefox, SpringBoard, Mail, Gmail, Outlook, Messages, Passwords, 1Password, Bitwarden, the authenticator apps, Find My, Settings, Photos, Health, Wallet, the App Store, Contacts, Phone, FaceTime, Files) and must be among the allowance's apps and any managed `allowedBundleIDs`; otherwise the command exits 1 with `app_not_allowed`, naming the `devices add` command for a person.
- Before each screenshot (and the session broker's and video frames, at most every 2 s within one command while no input is sent, and again after any input), each input batch and each detached touch, the runner checks that the pinned app is in front, by XCTest's active-app lookup (its accessibility client on Xcode 27.1 and later), and that the screen is on and unlocked. Otherwise the command exits 1 with `app_not_allowed`, or 7 with `device_locked` naming `offsider wake`, and neither reads nor touches the screen. A system alert, a sheet such as Siri's, Control Center over the app, and an iPad Stage Manager layout that reports SpringBoard, refuse until the app is in front again, so a screenshot on a device now starts the runner too. An Xcode with no lookup at all falls back to the app's own foreground state, which misses all of those, and says so in a notice. The runner speaks protocol version 3 and is rebuilt once after an upgrade.
- An iPad app in a Stage Manager window reports frames relative to its window, so element taps (`tap --id`, `tap --label`) are refused with `not_supported` and a hint to make the app full screen. Coordinate taps, screenshots and the tree itself still work.

## Screen sleep and wake

An always-connected phone can burn in, and `offsider sleep` and `offsider wake` control the screen from the Mac on any allowed iPhone or iPad, with no app in front. Both go through the runner, and each reads the screen first, reading only whether it is on and locked:

- `sleep` presses the lock button; a screen already off stays off and nothing is sent. It presses twice at most, as the first may only close a sheet.
- `wake` presses Home at most twice, once to light the screen and once to clear a lock screen with no passcode, and returns to the app that was in front. A screen already on and unlocked gets nothing, as Home would leave the app. When a passcode stays up it exits 7 with `device_locked`.

On a [test device](device-access.md#test-devices) this also happens by itself: the session broker runs the same check when it stops after `OFFSIDER_IOS_SESSION_IDLE` seconds without a command (default 300), `session stop` does the same, and the next command wakes the screen. An expired allowance or a lost device gets no press. Every command on a test device keeps the broker's idle clock running, and starts the broker when none is up. Over plain `ssh`, with no broker, the screen does not sleep by itself, so run `sleep`. Turn off Settings > Display & Brightness > Always On Display too, on a phone that has it.

## Limits

- `--verify` may take several screenshots: about 230 ms each from the stream, 2.3 s each through `devicectl`. Prefer `wait` or `assert` when the tree shows the effect. Screen comparisons on a device ignore the stream's compression noise, a drift of a few colour units, and `screenshot --compare` counts changed pixels and marks `--diff-output` by 8 by 8 block. `record-video` and `stream-video` build each frame from a screenshot, so their frame rate is low.
- `appearance` and `content-size` read and set the device through `devicectl`, and `orientation` turns it. The screen follows a new orientation only while the device is awake and unlocked and the app in front supports it; otherwise the command times out and says so.
- Refused on a device, with a message naming the alternative where there is one: `permission`, `status-bar`, `biometric`, `shake`, `posture`, `stream-video --format bgra`, `logs`, `rn prepare`, a `touch --down` without `--up` in the same command, `swipe` and `drag` with `--screenshot-at`, `boot`, `wake --unlock`, `stay-awake`, `unlock-code` and `credential` (when it would read the device, so pass `--app`). `credential --app <bundle-id>` saves or describes a test user without reading the device. Install apps with `xcrun devicectl`; `offsider app info`, `launch`, `stop` and `open` read, start, end and deep-link the pinned app through `devicectl` alone, with no runner.

## Signing in

`login` signs in on an added iPhone or iPad. On a [test device](device-access.md#test-devices) any saved login works, with no Touch ID. On any other, the login must be saved with `--devices any`, and each sign-in asks for Touch ID or your password. The username and password go only as key presses through the session broker, so they never reach `runner.log`: with no broker (Xcode 26, or no logged-in desktop) `login` exits 1 `not_supported` with nothing typed, and so does a character a US keyboard cannot type. Browsers and system apps are refused, as everywhere.
