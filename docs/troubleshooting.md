# Doctor and troubleshooting

`doctor` checks Xcode (`xcode.trust` passes for an Apple-signed Xcode in `/Applications`, warns for one elsewhere or chosen through `DEVELOPER_DIR`, and fails, skipping the framework checks, when the developer directory is not inside an Apple-signed Xcode; `xcode.private-api` fails when a private method Offsider calls changed type in this Xcode, so Offsider will refuse that call, and warns when CoreDevice is newer than the last version tested), Device Hub, CoreSimulator, HID settings, booted simulators and simulator crash loops, plus the Android SDK and adb server when an SDK is installed. With `--device` it checks one device instead: a simulator's state, Resize Mode, dtuhidd, HID transport, accessibility and recent crashes; an Android device (below); or an iPhone or iPad's `ios-device.*` checks (below). `--json` prints one object, and exit codes 3 and 4 mean warnings and failures.

With `--device`, `device.recording` warns while a `record-video` or `stream-video` runs on the device, naming its pid, since it holds back `login`, `wake --unlock` and `type --stdin` on a password screen; `offsider session stop --device <ID>` stops and saves it. `device.screen-reader` warns while a simulator tells its apps VoiceOver is on, saying whether Offsider turned it on (then `session stop` turns it off) or a person did; `offsider screen-reader off --device <ID>` turns it off either way.

Every report ends with the host: `host.load` (warns when the 1-minute load passes 4 per CPU), `host.disk` (free space in your home folder's volume: warns under 10 GB, fails under 2 GB) and `host.sessions` (other Offsider commands of yours, by subcommand and device only), then `install.bundle`, which reads every file bundled with Offsider through the digest compiled into the binary and fails, naming the first file that differs, when the install was changed (`brew reinstall offsider`), `install.skill`, which passes when every installed Offsider skill matches this version, warns `Run offsider init to update it.` when one differs (an agent, which has no terminal for `init`'s picker, is told `offsider init --client <client>` for each), and skips when none is installed, `install.rules`, which warns `Run offsider init --rules-only.` when Claude Code or Codex is installed without Offsider's permission rules or with an older one since replaced, and skips when neither is, and `install.deny-rules`, which warns when a deny rule that an agent loads (Claude Code's `settings.json` and `settings.local.json` in your home, this folder, its repository root and a worktree's main checkout, and Codex's `~/.codex/rules/offsider.rules`) also blocks the read-only `offsider devices add --plan`, such as `Bash(offsider devices add*)` from older setups. It matches rules as Claude Code does (`Bash(offsider devices add)`, with no `*`, matches only that exact command, so it passes), names the file and the rule, and leaves removing it to you: `devices add` itself refuses without a person at the terminal and Touch ID. `doctor` never edits the file and `--fix` never removes the rule; a missing, unreadable or malformed file is passed over. Without `--device`, a report with exactly one booted simulator or emulator ends with `Next: offsider doctor --device <ID>`. A person at a terminal sees a spinner while it checks, then a 🩺 header with the Xcode version and counts, the checks under This Mac, Android and the device as `✓`, `!`, `✗` or `-` rows, a `Fix` command under each warning or failure, and a closing line such as ❌ `1 failure · 1 warning` or ✅ `No problems found`, with the `Next` command on stderr. `--json` adds a top-level `host` object (`loadAverage`, `cpuCount`, `memoryGB`, `diskFreeGB`, `diskPath`, `sessions`), and with `--device`, `device.lease` reports any lease. Last come `managed.policy`, which lists each key a configuration profile forces as `key=value`, is skipped on an unmanaged Mac and fails on a key Offsider cannot read or does not know ([Managed Macs](mdm.md)), and `harness.managed`, which warns when a lock on Claude Code's managed settings drops the permission rules or the skill `init` installs ([Managed harnesses](agents.md#managed-harnesses)).

`--fix` applies safe fixes only: on Android, starting an absent adb server with `ADB_MDNS=0` (never when `--device` names a simulator); on an allowed iPhone or iPad named with `--device`, mounting the developer disk image.

For a physical device, `device.policy` comes first. A device no one allowed gets one failing `device.policy` check, with the `devices add` command as its hint, and no device checks run (`--fix` touches nothing); an allowed one passes it with its expiry. `doctor --device emulator-<n>` fails `device.policy` the same way when that serial is a USB device, or when adb cannot list devices to tell. `--json` adds a `policy` object for a physical device (`platform`, `id`, `allowed`, `refusal`, `expires`, `apps`, `managed`).

## Simulators

A simulator can fall into a crash loop after boot, with macOS showing a "quit unexpectedly" dialog for each crash. `doctor --device <UDID>` reads the crash reports macOS wrote in the last 10 minutes (only their header and process name, never paths or stack frames): `simulator.crash-loop` warns at two to four crashes of one process and fails at five or more (a busy host sees a few daemon crashes without a loop). Its fix is a quiet boot: shut the simulator down (`offsider shutdown <UDID>`), wait until the Mac is quiet, then boot it once. Erasing under load brings the loop back, so an agent is told never to erase it; only if it loops again on a quiet Mac does a person erase it with `xcrun simctl erase <UDID>`, which removes its apps and settings. Plain `doctor` lists every simulator with five or more crashes of one process as `simulators.crash-loop`, and `test-runner.sh` refuses to start on a simulator in a crash loop, with the same fix.

Simulator input goes through a warm input session ([details](input.md#simulator-input-session)). When input seems ignored after a simulator restarted or misbehaved, `offsider session stop --device <UDID>` closes it, and the next command opens a fresh one; `OFFSIDER_SIMULATOR_SESSION=off` opens one per command.

A swipe-up unlock on a simulator (after `button lock`) can freeze its display while the tree keeps changing. `screenshot` warns when its picture matches the last one although the elements on screen changed (both leave out the status bar and the bottom edge, which a frozen display still redraws), and names the way back: `offsider button lock`, then `offsider wake`. Unlock with `offsider wake --device <UDID>` in the first place, which presses Home at most twice while SpringBoard's lock screen is up and checks it has gone (exit 0 with nothing sent when it is not up, and `state_not_reached` when it stays): `button lock` says so.

After an app crash and relaunch, a simulator can return an empty accessibility tree while the app is plainly on screen. When `describe-ui` still reads an empty tree after its retries, it checks the simulator's `launchctl list` and warns when an app is running, and `doctor --device <UDID>` fails `simulator.accessibility` with `<bundle> is running (pid N) but its accessibility tree is empty`. Both print the fix: relaunch the app with `offsider app launch --restart`, then, if the tree stays empty, reboot the simulator. No simulator service restart was found that reliably brings the tree back, so `doctor --fix` does not try one.

When `describe-ui`, `screenshot`, `displays`, `rn logbox`, `rn devmenu`, `rn open`, a `--verify` or selector read, the read that places a coordinate `tap`, `swipe`, `drag`, `touch` or `gesture`, or the focus check of a plain `type` or `key-sequence` exits `device_unresponsive` after 30 s or more, that simulator or emulator stopped answering, even if others still do. Run `offsider doctor --device <ID>`; if a simulator is stuck, `xcrun simctl shutdown <UDID>`, then `offsider boot <UDID>`. Its app data survives. A frozen emulator is stopped with `offsider shutdown <serial> && offsider boot <AVD>`, which the error names in full.

On the iPhone Duo simulator's inner display, input goes through the simulator's input daemon (`dtuhidd`). When it refuses a connection, Offsider tries once more a second later; when it refuses again, the input exits 1 (`input_failed`) naming the daemon. Check it with `offsider doctor --device <UDID>`, then restart the simulator with `offsider shutdown <UDID>`, then `offsider boot <UDID>`: a daemon that has died stays down until then. Folding the simulator to its cover display also works.

## Android devices

`doctor --device <serial or AVD>` runs read-only Android checks (host checks only, no Xcode checks): the SDK, adb and its server (on loopback, and whether its mDNS discovery is off), the emulator package and the bundled helper; then the device's state (`android-device.state` fails for an emulator with full-disk encryption waiting at "To start Android, enter your PIN": Android reads booted, yet its storage is a small temporary disk, so app installs fail for lack of space until a person enters the PIN, which Offsider never types; the other device checks are skipped) and system image (an emulator without `arm64-v8a` is told to use one; a phone, whose image cannot change, is called untested), its RAM (`android-device.memory` warns under about 2.75 GB, with the `boot --memory 4096` hint), its screen (off when the display itself is off, even while Android reads the device awake, as a charging phone with Stay awake on does after its power button) and lock screen, and whether it waits for its first unlock since boot (`android-device.lock` fails then, with the same hints as `boot`, and warns on an unlocked device while its saved code is wrong or unconfirmed; `device.lock` in `--json` has the same fields as `boot --json`; on Android 9 and older, which do not name the credential, it reads whether one is set from the keyguard and says `unlock-code` takes a PIN or password only); stay awake; its gRPC endpoint with the auth mode (never the token); the UiAutomation slot and any accessibility service; one helper start with its times; any Metro reverse (shown, never changed; one `rn open` set is marked, and `session stop` removes it); and the system WebView's version (`android-device.webview` warns below 80, which cannot run web widgets such as Cloudflare Turnstile). The helper start holds UiAutomation for about half a second, so it is skipped while another Offsider helper runs.

After Android's framework restarts on an emulator (the boot animation shows again, often on a loaded Mac), there is nothing to do: the next command replaces the helper that outlived it, about 0.3 s slower, once. A read just after may say `no_window` until the launcher has drawn. If reads still fail with `helper_failed`, run `offsider session stop --device <serial>`, then retry; if they fail again, `adb -s <serial> logcat -d -s OffsiderHelper AndroidRuntime` shows why the helper stopped. An app that has stopped answering reads `app_not_responding` after about 5 s, and one that answers slowly gives a partial tree with a `Warning:` after 6 s; neither needs a restart of the emulator.

On a USB phone, the checks come from its row in adb's device list, the emulator gRPC check is skipped (the report says why), and `doctor` adds whether this Mac's adb authorisation lapses (Developer options > Disable adb authorization timeout) and whether automatic system updates can restart it. `doctor` never kills a process, restarts the adb server or changes a setting.

## iPhones and iPads

`doctor --device <UDID>` runs the `ios-device.*` checks: `xcode`, `coredevice`, `listed`, `transport`, `pairing`, `developer-mode`, `ddi`, `tunnel`, `lock-state`, `hid`, `ui-automation`, `session`, `usbmuxd`, `runner-signing` (which passes for a team from `OFFSIDER_IOS_TEAM_ID` or the allowance, and warns when only Xcode's signed-in teams exist), `runner-build` and `runner-trust`.

- `The developer disk image could not be mounted` is what `devicectl` says first for several causes, so Offsider reads the error beneath it: `device_locked` means unlock it, `developer_mode_off` means turn on Developer Mode and restart. If it still fails with the device unlocked and Developer Mode on, update Xcode, as this one's disk image may not cover the device.
- `ios-device.hid` opens the HID button socket and round-trips a barrier on it.
- iOS does not report the UI Automation setting, so `ios-device.ui-automation` is skipped with the Settings path unless the unlocked device refused input.
- `ios-device.session` reports the session broker and its screen stream, and is a skip when none is running: doctor never starts one. It names `caffeinate -d` when this Mac's display is asleep, and a terminal on the Mac's desktop when the process has no desktop session.
- `ios-device.usbmuxd` checks that usbmuxd lists the device on USB: usbmuxd can stop listing a wired device that `devicectl` still sees, until the cable is replugged.
- `ios-device.runner-build` reads the runner cache under `~/Library/Caches/offsider/runner/` for the device's team and prefix, and never builds: it passes for a cached build, warns with `offsider runner build --device <UDID>` when a provisioning profile in the cached build has expired or ends within an hour (the next start rebuilds it), warns with `offsider runner build --device <UDID>` when there is none (saying when that first build needs Touch ID), and fails when the last build's log shows another team owns the runner's App ID (naming the `devices add ... --runner-prefix` command) or the device is not registered (naming `runner build --register-device`). A prefix the variable and the allowance disagree on fails it with the exit 64 message.
- `ios-device.runner-trust` fails when the runner's last start on the device stopped at an untrusted developer certificate, recorded in `runner-failure.json` in the device's private folder and removed by the next start that answers: on the device, open Settings > General > VPN & Device Management and trust the developer certificate. It passes while a runner runs, and is a skip until one has started.
