# Device state

`appearance`, `content-size` and `orientation` change the device for every later screen, and `permission`, `status-bar`, `biometric` and `stay-awake` change state that outlives the command; each has a reset, so set them back when done. Setting a value already in place succeeds and says it changed nothing where the platform can read it. Set state before launching the app.

A running iOS app re-measures only some of its text after `content-size` changes, so headers can look cut short and a sheet can keep its old height, while the same screen is right after a cold start. When the size changes with an app in front (on a simulator, what answers at the screen's centre; on an iPhone or iPad, always, naming the allowance's only app when it pins one), a note on stderr names `offsider app launch --restart --app <id> --device <id>`, or for an Expo dev client `rn open` again with `--restart`; `--json` stays one object. Android recreates the app's screen, so it prints none.

At a terminal, a person sees a read as one line (`Appearance  dark`), a change as a ✅ receipt with what it was (`was light`), and state that outlives the command (a status bar override, stay awake on, a biometric enrolment, a permission, an Android orientation that turned auto-rotate off) with a 📌 note naming the command that undoes it. `permission services` and `show` are tables, and `displays` shows the posture above a row per display. An agent reads the same text as before.

- `permission` always needs `--app`; Offsider never changes every app's permissions at once. On Android it reads `dumpsys package` first, grants or revokes only what is not already in place, and also takes a literal `android.permission.NAME`. A service the app requests none of fails naming the manifest entries it needs; one it requests only some of applies to those and adds a note. `reset` revokes and clears the user-set and user-fixed flags so the app asks again (`reset all` also resets the app's app ops); before Android 13 `pm` cannot clear those flags, so there `reset` only revokes and adds a note when a permission stays user-fixed. It never runs `pm reset-permissions`, which resets every app. Android stops an app when one of its permissions is revoked, and the output says so. iOS simulators offer no read, so `show` is Android only and iOS reports earlier values as unknown.
- `status-bar` uses `simctl status_bar` on iOS. On Android it uses System UI demo mode in one adb round trip: `override` sets `sysui_demo_allowed` to 1 and sends the demo broadcasts, and `clear` exits demo mode and deletes the setting (the override's `--json` reports its earlier value, so a caller can restore it). Android cannot report whether demo mode is showing, and some vendor builds ignore it.
- `biometric` on iOS posts the BiometricKit notifications behind the simulator's Face ID and Touch ID menus: Face ID, or Touch ID on the iPhone SE and iPads other than iPad Pro (`--modality` overrides). On an Android emulator `match` touches the fingerprint sensor with finger 1 and `no-match` with finger 10 through the emulator console (`adb emu finger`, `--finger-id` overrides). `match` and `no-match` are events: nothing confirms the app saw them, so check its screen. Enrolling a fingerprint on Android needs a screen lock, which Offsider does not set, so `enrol` there explains how to do it in Settings.
- `permission`, `status-bar`, `stay-awake`, `airplane`, `wake`, `sleep`, `unlock-code`, `appearance`, `content-size` and `orientation` work on an allowed USB phone and change the phone itself; `biometric` is refused there. On a phone, `permission --app` (`show` included) must name an allowed app that is not a browser or system app, else exit 1 `app_not_allowed` with nothing sent, and `permission grant|revoke|reset all` exits 64: name the services, since `all` reaches SMS, the call log and location and outlives the run. `status-bar override` and `stay-awake on` print a note that the setting stays, with the command that undoes it. Location simulation is not offered.

## Permission prompts

`offsider alert show|accept|deny|choose "<label>" --app <id> --device <id>` reads or answers the prompt the system shows when an app asks for a permission: Android's runtime permission dialog, or an iOS alert such as “App” Would Like to Send You Notifications. Without it, a run stops for a person at every prompt, since the window in front is not the app.

| Device | `alert` |
| --- | --- |
| iOS simulator, Android emulator | Yes |
| Android, iPhone or iPad test device ([chosen by a person](device-access.md) in `devices add`) | Yes |
| A phone in personal use | Never: exit 1 `person_required`, nothing read or sent; the prompt is the user's |

- `show` prints the prompt's text and each button, marking the one `accept` and `deny` would pick, and changes nothing. `--json` prints `{"version":1,"device","platform","app","action","prompt":{"title","message","source","buttons":[{"label","role","frame"}]},"button","next","untrusted"}`; `role` is `accept`, `deny` or `other`.
- `deny` picks the declining button. `accept` picks the granting button with the narrowest grant that lasts, by the same rule on both platforms: While using the app on Android (else a plain Allow), Allow While Using App on iOS (else Allow, or OK on an older iOS). It never picks a broader grant (All the time, Always Allow, Allow Full Access), a one-time grant (Only this time, Allow Once), a photo picker or a Continue that opens a second sheet: `choose "<label>"` picks one of those, by the button's whole text (quote style and spacing aside). A lasting grant is the default because it behaves like `permission grant` and is undone by `permission reset`, where a one-time grant lapses in the middle of a run.
- Android buttons are told apart by their resource ids, so a device language changes nothing. iOS buttons are told apart by one table of English labels. A privacy prompt's ids (seen for camera, contacts and tracking) decide in its place only where the table knows no label, as in another language, and then only between two buttons, so an id never makes a broader grant the default. Notifications and location prompts carry no ids: in another language `accept` and `deny` exit 6, naming the buttons for `choose`.
- On iOS, `accept` and `deny` act only on a privacy prompt (by its id) or a title in the shape of a permission request: “App” Would Like to …, or Allow “App” to …. Any other SpringBoard alert that names the app first is for `show` and `choose` only.
- It answers only a prompt the system ties to `--app`. On Android: the resumed activity is the permission controller's runtime request, and Android records `--app` as the caller that started it, by package name and by uid. On an iOS simulator: SpringBoard owns the screen, the only app card beneath its alert is `--app`'s, and the first name the alert's title quotes is that app's. On an iPhone or iPad: the runner reads SpringBoard's alert alone, never the app (which an alert holds), `--app`'s process is in the foreground beneath it, XCTest lists no other app as active, and the first name the title quotes is the app's display name, which `devicectl` gives. Another app's prompt, a system alert that names no app, a crash dialog, an update prompt, a save-password sheet or anything else the system drew exits 7 `system_prompt_in_front`, naming it; no prompt at all, on a second read 0.6 s after the first, exits 2 `alert_not_shown`, naming the app in front. Nothing is sent in either case. `login` keeps its own handling of save-password prompts.
- `accept` and `choose` are held to the app's [guard rules](guard.md): a `never` rule on the button refuses, an `ask` rule waits for a person at the Mac, and a rule scoped to a screen, or one that makes a screen look-only, holds too, since the screen beneath a prompt cannot be read. `deny` always passes.
- A prompt slides in, and a button read mid-slide is a row off, so before answering the command waits for two reads 200 ms apart to give the same text and frames (exit 1 `screen_not_idle` when it is still moving after 3 s). It reads the prompt once more just before the tap, on both platforms (exit 1 `foreground_changed` when it left or changed), taps only a button whose middle lies inside the prompt (exit 2 `target_off_screen` on a prompt that scrolls), and then watches the screen on a clock: for one second after the tap for a prompt that follows, as when the app asks for several permissions in turn (printed, and `next` in `--json`), and for up to 4 s for the answered prompt to go (exit 5 `not_verified` when it stays).
- On an iPhone or iPad the runner taps the button by its label, in one step that first checks the alert still has the title read and the button the frame read (exit 1 `foreground_changed` otherwise); the runner must be version 5, which Offsider builds when it needs it.
- The answer outlives the command. `offsider permission reset <service> --app <id>` makes the app ask again on a simulator or an Android device; `permission` cannot change an iPhone's privacy settings, so there change it in Settings, or reinstall the app, which resets that app's alone. E2E suites reset what they answer, for that app only.
- In an [evidence run](capture.md#evidence-runs), each answer is a line in `manifest.ndjson` and the timeline with `prompt` (the title) and `button` (the one chosen); a refused `accept` keeps the title and no button.
- On an Android, iPhone or iPad test device held to one app with `--app`, `describe-ui` and `screenshot` read that app's permission prompt instead of exiting 7: `describe-ui` names it as a read-only system window, and [`screenshot`](capture.md#masks) shows the prompt alone, with everything outside it painted and `maskUnproven: "prompt"`. Input stays refused there; `alert` answers it.

What it cannot prove: on an iPhone or iPad, that the alert was raised by the app beneath it rather than shown over it by the system (the title naming the app is the evidence). On an iOS simulator or device, that an alert with no privacy id is a permission request rather than another SpringBoard alert worded in one of those two shapes (a paste request reads “App” would like to paste …; its buttons are in no table, so only `choose` answers it), that the English words mean what they say on a later iOS, and that a background app with the same display name did not raise it. On Android, a build that renames the permission controller's package or changes the layout of `dumpsys activity activities` is refused, not guessed at, and so is an app in a work profile or a second user. Other consent screens (battery optimisation, screen capture, VPN, Bluetooth, notification access) are not permission requests and are refused.

## Apps

`offsider app info|launch|stop|open|install|uninstall|prefs|broadcast --app <id>` reads or drives one app and reaches nothing else on the device. Without `--app`, it takes `offsider.login.json`'s `bundleId` or `package`, then a physical device's only pinned app; with neither it exits 64.

```bash
offsider app info --app com.example.app --device <DEVICE_ID> --json
offsider app launch --restart --app com.example.app --device <DEVICE_ID>
offsider app stop --app com.example.app --device <DEVICE_ID>
offsider app open 'https://example.com/offer?id=7&ref=push' --app com.example.app --device <DEVICE_ID>
offsider app install build/app-debug.apk --app com.example.app --device <DEVICE_ID>
offsider app install Build/Products/Debug-iphoneos/Example.app --app com.example.app --device <DEVICE_ID>
offsider app uninstall --app com.example.app --device <DEVICE_ID>
offsider app launch --cold --json --app com.example.app --device <DEVICE_ID>
offsider app prefs --app com.example.app --device <DEVICE_ID> --json
offsider app broadcast com.example.app.action.REFRESH --app com.example.app --device <DEVICE_ID>
```

- `info` reads the version and build: `simctl appinfo` on a simulator, `devicectl device info apps --bundle-id` on an iPhone or iPad, and `dumpsys package <package>` on Android, which adds the installer (`com.android.vending` is Google Play; none for adb), first install and last update times (read in the device's time zone; null without one), whether the build is debuggable and, from Android 13, whether it may post notifications. An iPhone app built and installed by a developer reads installer `developer`. `--json` prints `appVersion`, `build`, `installer`, `firstInstalled`, `lastUpdated`, `notifications` and `debuggable`, null where the platform does not say, and lists the app's own text in `untrusted`.
- `launch` starts the app as a tap on its icon does; a running app comes to the front. `--restart`, or its other name `--cold`, stops it first. It reports `start`: `cold` for a new process, `warm` for one already running; Android starts the launcher activity with `am start -W`, calls the start cold when the app's process id after it is new, whatever Android's own launch state says, and adds `TotalTime` (`milliseconds`), `WaitTime` (`waitMilliseconds`), Android's raw `LaunchState` (`launchState`) and the new process id (`pid`). `logs --rn --app <id>` then collects that launch's app logs. An app with no launcher activity is refused with a pointer to `app open`.
- `stop` ends the app's process and says whether one was running: `am force-stop` on Android (which, like Settings' Force stop, also clears the app's notifications and alarms), `simctl terminate`, or `devicectl device process terminate` for the process inside the app's bundle. On an iPhone or iPad the app is the process directly in its bundle, so an extension is not stopped and does not count as running; when `devicectl` names no bundle location, `stop` exits 1 and stops nothing, and `launch` leaves `start` `null`.
- `open '<link>'` sends one link to the named app alone. Android runs `am start -W -a android.intent.action.VIEW -d '<link>' <package>`, quoting the link whole for the phone's shell so `&`, `?` and `;` reach the app, and limiting the intent to the package so no browser opens; when two of the app's own screens take the link Android still shows a chooser, and that, or another app taking the link, exits 1 with `link_not_handled`. `--restart` asks Android first, so a link it knows no screen for, or would send to a chooser, stops nothing; a refusal after the stop says the app was stopped. An iPhone or iPad gets `devicectl device process launch --payload-url`, which the app receives as an open-URL call, not as the user activity a tapped universal link brings; iOS reports only that the link was delivered, so exit 0 means that, the output says `Sent the link to` and `linkHandled` is `null`, and `link_not_handled` cannot occur: `wait` for the screen. A simulator has no per-app link, so `simctl openurl` lets iOS pick the app that claims it, and Offsider then checks the named app is in front on two reads; another app taking it is `link_not_handled`. An `https` link there opens in Safari, not in the app that claims its domain, as `simctl` hands web links to Safari: test a universal link with the app's own scheme, or tap the link inside a page. When iOS 27 first asks `Open in “<app>”?`, Offsider taps Open once, and only on the prompt that names the app the link went to, as `rn open` does. Links are one line of printable ASCII up to 4 KiB with a scheme (percent-encode spaces); `intent:`, `file:`, `content:`, `javascript:` and `data:` are refused (exit 64), since they reach other apps, files or code. On Android and a simulator a link no screen of the app takes exits 1 with `link_not_handled`, and `--json` says `"linkHandled":true` once one did.
- `info` only reads. `launch`, `stop` and `open` lock the device like input and work on an allowed phone, iPhone or iPad, where the app must be one the allowance permits: a browser, home screen, system app or an app managed policy denies exits 1 `app_not_allowed` with nothing sent, on a phone allowed for any app too. On an iPhone or iPad they use `devicectl` alone, so no runner or session broker starts, over USB only; a locked one exits 7 `device_locked`.
- `install <path>` takes the file the device needs: an `.apk` on Android, a built `.app` folder on an iPhone, iPad or simulator. Either way Offsider reads the app's id from the file on the Mac and refuses one that is not `--app` with `package_mismatch` before sending a byte; on an emulator, a simulator or a test device `--app` defaults to the file's own id. It replaces an installed copy and keeps its data. `--json` prints `path`, `replaced`, `bytes` and `milliseconds` (Android also keeps `apk`, the same path).
- On Android it reads the package from the APK's zip and binary manifest, with no SDK tool, then streams the file with `cmd package install --pkg <package>`, so Android enforces the same package itself and no copy lands on the device. A copy signed differently or newer exits 1 `install_failed`, naming the uninstall that fixes it. A file that is not an APK, a bundle (`.aab`) or one with two manifests exits 1 `apk_unreadable`. Split APKs are not installed. A USB connection lost mid-file says nothing was installed, and that the same command can be run again.
- On an iPhone or iPad it reads `CFBundleIdentifier` from the bundle's `Info.plist`, then clones the bundle into a private 0700 folder and checks the clone, so what was checked is what is sent: every app and extension inside (`PlugIns`, `Watch`, `AppClips`) must carry an id under the app's own (`package_mismatch`), no link inside may point out of the bundle (`bundle_unreadable`), and the embedded provisioning profile must not be expired and must list the device (`not_provisioned`; a profile that cannot be read is sent, and the device decides). It then runs `devicectl device install app` on the clone, reads the id the device says it installed, removes it at once and exits 1 if that is not the allowed app, and deletes the clone. The clone is private to your user account, not to the one command, so the id the device reports is the last check. A simulator build, an `.ipa` (unzip it and pass `Payload/<name>.app`) and a folder that is not a `.app` exit 1 `bundle_unreadable` before any device stack starts. A device's own refusal (no valid profile, a bad signature, no room, an iOS too old) exits 1 `install_failed` in the device's words with the fix. Offsider never builds, signs or registers a device, and passes no provisioning flag: when the profile does not cover the device, a person adds the device to the team in Xcode and the app is built again. It uses `devicectl` alone, over USB only, with no runner or session broker; a locked device exits 7 `device_locked`.
- iOS, unlike Android, lets a development build from the same team install over an App Store or TestFlight copy and take over its data. So on an iPhone or iPad in personal use, installing over such a copy, or removing one, needs a person at the Mac: in a terminal it asks for Touch ID or the password, and an agent exits 1 `person_required` with the whole command to hand over. A copy a developer installed, a test device and a simulator have no such step. iOS keeps an app's Keychain items after it is removed, so an app that reads as not installed may still have saved logins a later build can read.
- On a simulator it installs the checked clone with `simctl install`, and takes a simulator build only: a device build exits 1 `bundle_unreadable`.
- `uninstall` deletes the app's data too (`pm uninstall`, `devicectl device uninstall app`, `simctl uninstall`); an app that is not installed is no error (`wasInstalled` says so). On a phone, iPhone or iPad `install` and `uninstall` need the app pinned by name, as they change its data: a phone allowed for any app exits 1 `app_not_allowed`. A test device needs no pin.
- `prefs` (Android) lists each file in the app's `shared_prefs` folder with its key names and types (`string`, `int`, `long`, `float`, `boolean`, `set`). Values never leave the device: its own `grep -o` prints only each key's opening tag through `run-as`, and no option asks for a value, a length or a hash. The Mac keeps only lines of that exact shape, never repeats anything else the device printed, and masks a key name shaped like a token as a log line would. An active run gets a manifest line with the key count (`entries`); the tree cache is not touched. It needs a debuggable build, as `run-as` does: a release build exits 1 `not_debuggable`, naming `app install` as the fix. Android's binary preference files are listed with their keys left out.
- `prefs` then lists the key names in the app's React Native AsyncStorage database: `databases/RKStorage`, or `databases/AsyncStorage` when the app uses the library's Room storage (with both, the Room one unless it is not AsyncStorage's shape, and a note names the other). No value leaves the device here either. The database is read a page at a time through `run-as`, with no `sqlite3` on the device: its 100-byte header, in write-ahead mode the log's header and each frame's 24-byte header, the schema page, then only the pages of the key column's automatic index, which hold key names and row numbers. The device prints a page only after checking it is the schema page or an index page and that the file's page size has not changed, and leaves out the page's free space, so a row cannot leave even when the app rewrites the file mid-read. A database is read only when the key index is its one index. Names are masked and cut at 200 characters as preference keys are (a numeric id inside a name is not masked), and counted in the run's `entries`. A name too long for its page is listed cut short and counted in `cut`, as its overflow pages are never read. `--json` adds `asyncStorage`: `null` with no database, else `database`, sorted `keys` and `cut`. A database the app writes to during the read is read once more. One that cannot be read never fails the preference listing: `keys` is empty and `unread` says why in one word, so check it before asserting a key is absent. The words are `changing` (it changed twice: `app stop`, then run it again), `unfinished` (a write the app did not complete: run it again, or open the app once), `utf16`, `schema` (not AsyncStorage's own table and index: another table shape, a `WITHOUT ROWID` table or a second index, whose pages could hold values), `format` (not SQLite, or encrypted), `corrupt`, `large` (over 4,096 index pages or 1,024 log frames) and `failed` (the device did not answer: run it again). A frame in a write-ahead log is told from a stale one by its salts and commit markers, not its checksum, which needs the page. A database under another name, MMKV, DataStore and `expo-sqlite` are not read.
- `broadcast <action>` (Android) sends `am broadcast -p <package>`, or `-n <package>/<class>` with `--receiver`, so nothing else on the device hears it. A stopped app still gets it (`--include-stopped-packages`). This is how to refresh a home-screen widget: send the action the widget's provider declares. Android keeps system actions such as `android.appwidget.action.APPWIDGET_UPDATE` from the shell, which exits 1 `broadcast_refused` and lists the app's own actions. Android would drop one sent to a receiver that is not exported with no word of it, so Offsider exits 1 `broadcast_refused` with nothing sent; a `--receiver` the app lacks exits 1 `receiver_not_found`. An action no manifest declares is still sent, for a receiver the app registers while running, with a note. `resultCode` is what the receiver set, and `receivers` lists those its manifest declares for the action. It takes no extras.
- `prefs` only reads. `install`, `uninstall` and `broadcast` lock the device like input. On a simulator, iPhone or iPad `prefs` and `broadcast` exit 1 `not_supported`.

A person can allow these commands once in their agent's rules rather than approve each call. `offsider init --print-rules` lists the exact lines under `allowOnce`; `init` never adds them by itself. For Claude Code, under `permissions.allow`:

```json
["Bash(offsider app install*)", "Bash(offsider app uninstall*)", "Bash(offsider app prefs*)", "Bash(offsider app broadcast*)", "Bash(offsider airplane*)"]
```

## Airplane mode

`offsider airplane` reads Android's airplane mode, and `on` or `off` sets it with `cmd connectivity airplane-mode` (Android 11 and later), checking the setting took.

```bash
offsider airplane on --device <DEVICE_ID>
offsider session stop --device <DEVICE_ID>
```

- It outlives the command and a reboot, so Offsider records that it turned it on, in the private directory's `airplane/`, before asking Android. `session stop` (and `devices remove`) turns it off only then, and `airplane off` drops the record. Already on when you ran it, it stays on: `resetBySessionStop` in `--json` says which. `session stop` names a device it could not reach with the command that retries it, and `session status` lists the record; a stop drops a record for a device not connected for 30 days.
- A phone allowed for any app takes it, as it names no app. An unnamed `session stop` leaves a phone that is no longer allowed alone. An AVD is found by name, so `--device` takes its name or serial, another AVD on the same serial is left alone, and a stopped AVD's record waits for it.
- USB stays connected. An emulator loses its route to the Mac at `10.0.2.2`, so a React Native debug build cannot reach Metro until it is off.
- This is the way to test an app offline: on API 36 an app's connections fail at once with no route, and they work again about 10 s after `session stop`, so wait before you read the result. An iOS simulator shares the Mac's network, so it cannot go offline alone; fake the failure in the app there.

## Orientation

`orientation` reads or sets the device orientation, waiting until the device has turned: `portrait`, `landscape-left`, `landscape-right`, `portrait-upside-down`, or `--rotation 0|90|180|270` in degrees anticlockwise. The names say how the device is turned, as Maestro and devicectl name them: `landscape-left` is turned 90 degrees anticlockwise, home edge on the right, which React Native's and UIKit's interface orientation call `landscape-right`. `describe-ui` and `screenshot --json` report the shape as `orientation` and the turn as `rotation`. An iOS simulator can hold a turn its screen never showed, which a later app or fold takes, so Offsider tells it the orientation even when its screen already shows it, and turns back a turn that times out. When a simulator's turn times out, the error also says what to try next: press Home, turn to portrait and launch the app again, which clears an app that has stopped following turns.

`--json` on Android also reports `autoRotate {before, now, restored}` and `userRotation {before, now}` (null on iOS). On Android, `orientation` turns auto-rotate off while the device is turned: the first turn in a boot, to any orientation, records auto-rotate and `user_rotation` in the private directory's `orientation/` (one 0600 file per serial, naming the boot by the emulator's start time or a phone's kernel boot id), and `orientation portrait` writes auto-rotate back, and `user_rotation` too when auto-rotate was on, then removes the record. It does so even when the screen already shows portrait, as after a turn the app in front refused, and puts auto-rotate again when one write does not read back. A portrait the app in front refuses still puts them back, then times out naming the next step. With auto-rotate back on, a phone's screen follows how it is held, so `orientation` watches it for a second and reports what it shows, warning when the sensor turned it away; an emulator's stays put. When auto-rotate cannot be read or recorded, `orientation` fails before turning, so auto-rotate is never left off without a record.

## Foldables

A foldable has a `cover` and an `inner` display, and one of them is active at a time; `main` names the only display of a device with one, so `--display main` on a foldable exits 64 with `unknown_display`. `offsider displays` lists both and marks the active one, and `offsider posture` reads the posture (`closed` uses the cover display, `open` the inner one). `describe-ui`, `tap` and the other input commands use the active display, and `screenshot` captures it unless `--display` names the other one. `describe-ui --display inner` fails with a hint while the inner display is not active, so a script can check it is reading the screen it expects.

- iOS: `posture` folds and unfolds the iPhone Duo simulator by driving its hinge the way Device Hub does (a private CoreDevice path, best effort on Xcode 27.1; where the runtime has no hinge service the command says so and exits 1). Only the hinge tells half-opened from open: Offsider reads it from the simulator's own log (about 1 s), which also sees a hinge moved in Device Hub, and names the posture as the simulator reports it to apps. Folded, the cover display is 466 x 678 pt; unfolded in portrait, the inner display is 951 x 669 pt (landscape-shaped, rotation 0: `screen.rotation` is the device's turn from portrait, as `orientation --json` reports it, not the UI's turn on the panel). `orientation` turns the Duo folded or unfolded, as Device Hub's orientation picker does, and a turn outlasts a fold; the cover's home screen stays portrait, as on any iPhone. A hinge request the simulator refuses does not fail the command when the device reads the posture anyway. When the hinge and the display disagree, as they can while a move lands, `posture` warns with both reads and the angle, a timeout's error names them, and `--json` adds `disagreement`: `{"hinge":"open","angle":120,"display":"open"}`.
- Android: `offsider posture open` (or `closed`, `half-opened`) folds the emulator through its gRPC endpoint, or `cmd device_state` over adb, and waits until the device reports it. A Pixel 9 Pro Fold emulator's inner display is about 852 x 883 dp and its cover display about 443 x 994 dp. Folding it shows "Swipe up to continue" on the cover, over the app, which keeps running: swipe up from the bottom edge to use it.
- Android phones: a foldable phone such as a Samsung foldable lists `cover` and `inner` like the emulator, and `posture` reads One UI's `CLOSE`, `HALF_FOLDED` and `OPEN` states as `closed`, `half-opened` and `open`. `posture closed`, `half-opened` or `open` sets the phone's state with a `cmd device_state` override (gRPC is emulator-only), the same allowance covering it as `orientation`; no new grant is needed. Offsider first records the override (the state and the phone's boot id) in the private `postures/` folder, then sets it, and prints `offsider posture reset --device <serial>`, which drops the override so the hinge decides again. The override lasts until that reset or a reboot; `session stop` and `devices remove` also reset it, but only while it is still the one Offsider set on the same boot (a bare `session stop` only on phones still allowed), and a phone that is not connected keeps its record for the next stop. Each names a phone it left with `offsider session stop --device <serial>`, and `session status` lists the record. A set or reset that fails leaves the record of the override still in place. Setting a posture replaces an override someone else set, and a reset then returns to the hinge's own state. `posture reset` works on an emulator too, and refuses an iOS simulator.
