# React Native and Expo apps

## Ids, labels and roles

- `testID` is `id` and `accessibilityLabel` is `label` on both platforms (on Android from `content-desc`).
- A `View` with neither `accessible` nor `testID` can be flattened away on Android, so ask for a `testID` when a target is missing. A `Pressable` without a label takes its children's text as its label.
- Rows without a `testID` or `accessibilityLabel` take their children's text as the label (`Inbox, 3 unread`), live values included, so `--label` stops matching when a value changes. Prefer `--id`; otherwise find the row in `describe-ui --summary` and tap its centre.
- Checkboxes, radio buttons and switches report their role on both platforms, with `value` `1`, `0` or `2` (mixed), so `--element-type radioButton` works on iOS too. On iOS a combo box and a progress bar may still read as `other`; select those by `--id` or `--label`.
- `offsider button back` pops React Navigation and custom stacks on Android, like the hardware back button.

## Kept-mounted views

- Closed bottom sheets and the previous screens of a JavaScript stack often stay mounted. On iOS they stay in `describe-ui` with frames outside the screen; on Android nodes the user cannot see are left out.
- Selectors, `wait` and `assert` count only on-screen matches, so open the sheet, then `wait --id <id>` before tapping inside it; add `wait --settled` when it slides in. A partly visible element is tapped at the centre of its visible part.
- A previous screen still partly on screen under the current one keeps its ids. A selector takes the match on the page drawn over it when Offsider can tell the page covers it; when `--id` still reports multiple matches, add `--topmost` to tap the page on top (or `--nth <n>` from the candidates' `index`). On Android a page reported as not visible to the user never counts as covering it.
- On Android a `Modal` is its own window, so only the modal is in the tree while it is open; `describe-ui --summary` then starts with `# window: <title> (modal)`, or the package when the modal has no title.
- Content under `accessibilityElementsHidden` or `importantForAccessibility="no-hide-descendants"` (apps often wrap charts and web views this way) is missing from the tree, buttons included, but still takes taps. Tap by coordinates and say so, or ask for the wrapper to expose its controls.
- Charts, maps, canvases and web views change pixels, not the tree: check them with `wait --region <x,y,w,h> --changed` or `screenshot --region <x,y,w,h> --compare before.png`, and with the app's logs.

## Cloudflare Turnstile

A Turnstile checkbox is for a person: never tap it, its label or its coordinates. `offsider turnstile` only reads its state, and `login` stops with `turnstile_required` when a widget is on screen. Read `offsider guide turnstile` for how to ask the user and carry on by yourself, and for builds that use Cloudflare's test keys.

## Logs

`offsider logs --rn --device <DEVICE_ID>` prints `console.log`, `console.warn` and `console.error` output from the last 30 s, in release builds too, and is the best check that an action did something a screenshot cannot show, such as a request being sent. Prefer `logs --rn --app <bundle id or package>`: an app's own logger often writes outside React Native's log, and on Android it keeps lines from before a restart. Windows, filters, `--json` and redaction are in `offsider guide evidence`.

- On iOS every `console.warn` can arrive twice, once as `javascript:` and once as a copy under the app's process, when a monitoring SDK that wraps `console` logs its own. Drop the copies with `logs --rn --app <bundle id> --exclude '<text only the copies carry>'`, which keeps them out of the evidence run too; a pipe through `grep -v` would not.
- A long error ends `<…> [truncated]` (`"truncated": true` in `--json`) on iOS, which stores only about 1 KB of a message; the rest cannot be read from the log. In a debug build, `rn logbox open` and then `describe-ui` show the whole error. Otherwise log it in chunks under 1 KB from the app. On Android a message past about 4 KB loses its end with no marker, and each line of a multi-line message is its own entry.

## Debug builds

- Debug builds load JavaScript from Metro. An Expo dev client that cannot reach Metro shows its launcher instead of the app (`Development Build`, `Searching for development servers...`, `RECENTLY OPENED`). Run `offsider rn open --port <metro port> --bundle-id <bundle id or package> --wait-id <id on the first screen> --device <DEVICE_ID>`: it checks Metro answers on 127.0.0.1, sends the dev client its link to Metro (resending while the launcher shows, and tapping Open on an iOS simulator's `Open in` prompt within 10 s of its own link), and waits through `Bundling` until the id is on screen (`--timeout`, default 180 s; a cold bundle can take minutes). Without `--wait-id` it waits until the screen shows something and holds still for a second: an app window that is empty, or holds only Expo's dev menu button (`Tools`), as while the bundle loads, never counts, and a timeout says whether the `Bundling` banner was still showing or the window stayed empty. On an Android emulator the banner may never reach the tree during a cold bundle (the playground's debug build lists no window for it), so prefer `--wait-id` there. Exit 9 (`metro_not_running`) means ask the user to start Metro; exit 1 (`rn_load_failed`) means the app showed a load error, so read `logs --rn`. It also checks the app's process every 2 s, so a crash while loading fails fast with exit 1 (`app_crashed`), naming the newest iOS crash report or the Android exception class or signal, instead of waiting out `--timeout`. A timeout that ends on a blank screen says so: run it again with `--restart`, which stops the app first (as `rn prepare` does) so the link opens it fresh; `rn open` never restarts the app by itself. It also stops early, without blaming Metro: exit 5 when the app holds a screen without the `--wait-id` element for 15 s (the message names the screen's first id; pass an id of the screen the app opens on), exit 5 when Expo's dev menu intro covers the app (run `rn prepare`, then `rn open --restart`), exit 1 `person_required` on an iOS simulator when a system prompt such as a permission alert covers it (it names the prompt and its buttons and never answers it: ask the user which to choose), and with the read's own error when tree reads fail for 10 s (on Android, `app_not_responding` when the app is in front but has no window: run `rn open --restart`). On a phone allowed for any app it reads only `--bundle-id`. An Android emulator reaches Metro at 10.0.2.2 unless an `adb reverse` maps the port. A phone needs that reverse: `rn open` sets it only for a port the user chose under Metro in `devices add`, else exit 7 `metro_port_not_allowed` (ask them to run `offsider devices add` and choose the phone and port; never run `adb reverse` yourself); `session stop --device <serial>` removes it.
- A cold bundle can take minutes to load, so give the first `wait` after a launch a long `--timeout` (up to 900 s).
- Testing offline on an emulator: airplane mode, `svc wifi disable` and `svc data disable` also cut the dev client's route to Metro at `10.0.2.2`, so Metro goes quiet and a reload shows the launcher. A dev client pointed at `localhost:<port>` over an `adb reverse` keeps reaching Metro in airplane mode, since the reverse runs over adb. Blocking one app's network (`cmd connectivity set-package-networking-enabled`) also blocks its loopback on API 35 and 36 and does not exist on API 34, so Offsider has no `network` command. The app sees `onLost` within about a second of airplane mode, and `logs --rn` keeps reading the device log throughout; turn the network back on before reloading.
- Slow networks: nothing slows one device. The emulator console's `network speed` and `network delay` (and the `-netspeed` and `-netdelay` launch flags) show in `network status` but left traffic at full speed on emulator 37.1 with API 36, over Wi-Fi and mobile data alike. An iOS simulator shares the Mac's network, so Network Link Conditioner slows the whole Mac and every other session's devices; a physical iPhone has its own under Settings > Developer. Prefer a slow or failing response from the app's own mock layer.
- Debug builds raise a LogBox toast at the bottom of the screen for `console.error` and uncaught errors, often over the tab bar (`console.warn` raises none; read warnings with `logs --rn`). It is in the tree (role `other` on iOS, `button` on Android), labelled with `!` or a count and then the message, such as `!, Request failed`, and `describe-ui --summary` starts with `# logbox: 2 logs`. `tap` refuses a target it covers on both platforms, including one whose point is just above its frame or anywhere below it, as its touch area runs from a point above its top edge (on an edge-to-edge Android app, the status bar's height higher still) to the bottom of the screen (`coveredBy` `evidence` `logBoxTouchArea`); a target whose frame only reaches that area gets a warning. Note the text, then clear it: `offsider rn logbox dismiss --device <DEVICE_ID>` taps each toast's clear button, or opens the inspector and taps `Dismiss` once per log, and exits 5 when logs remain. `rn logbox status` lists each toast's message without a tap, numbered from 1 at the bottom (`--json`: `{logs, toasts: [{index, count, message, frame}], inspector, emptyDialog}`; messages are redacted unless `--no-redact`). `rn logbox open --index <n>` opens the inspector on toast n so `describe-ui` shows the whole log, and `rn logbox dismiss --index <n>` clears only that toast. A banner's label holds line breaks, so `tap --label` with its visible text often misses; the miss then names the toast and these commands.
- A tap that lands on a toast opens the full-screen LogBox inspector, which is in `describe-ui` (`Console Error`, `Log 1 of 1`; the summary says `# logbox: inspector open`): `rn logbox dismiss` or `tap --label Dismiss` clears the log and closes it, `tap --label Minimize` returns to the toast. On Android the inspector, the dev menu and its intro are separate windows, so while one is open `describe-ui` lists only that window and the app's elements seem to be missing. A caught render error (an error boundary's fallback) opens the inspector by itself, so `wait` or `assert` for an app element stops after 1.5 s with `logbox_inspector_open` (exit 1) instead of running its whole timeout; run the `hint` (`tap --label Minimize`, or `rn logbox dismiss`), then wait again. On iOS the app stays in the tree under the inspector and the wait passes; a timeout there adds `LogBox inspector open` to its `last:` reason.
- On Android, React Native can leave its LogBox dialog up after the last log goes: an empty black screen, `# window: <package> (modal, empty)` in `describe-ui --summary`, `emptyDialog` true in `rn logbox status --json`. `rn logbox dismiss` then exits 5 with `emptyDialog` true and taps nothing more. Reload the app to close it (in an Expo dev client, `rn open --port <metro port> --bundle-id <package>`); Back closes it too, but the app also handles that Back press, and React Native can crash when the inspector next opens.
- A fresh install of an Expo dev client opens its dev menu intro over the app: run `offsider rn prepare --bundle-id <bundle id or package> --device <DEVICE_ID>` before the first launch to skip it, or dismiss it with `tap --label Continue`, then `tap --id xmark` (on Android `tap --label Close --element-type button`). `rn prepare` needs a debug build and stops the app if it is running.
- `offsider rn devmenu --device <DEVICE_ID>` opens the dev menu (a shake on an iOS simulator, the menu key on Android emulators and phones, which `button menu` also sends) and lists its items, marking those the app registered as custom (after `; custom:` in the line, `"custom":true` with `--json`; choose one with `--label`); `rn devmenu reload` (or `home`, `inspector`, `perf-monitor`, `fast-refresh`, `debugger`, `close`, or `--label <text>`) taps one and waits for the menu to close (with `--json`, one object: `{"version":1,"menu":"expo","item":"reload","label":"Reload","closed":true}`, `item` null for `--label`); on Android `--label 'Open React Native dev menu'` switches to React Native's own menu, which then lists its items and has no close control, so `close` presses Back there and checks the menu went (`"label":"Back"`). Exit 2 means the menu has no such item (the items are the candidates), or, with `target_off_screen`, that the item is past the fold of the menu: nothing was tapped, so run the `hint` (a `swipe` inside the menu), then `rn devmenu` again, which uses the menu that is already open. Exit 1 means it never opened (a Release build has none). On Android an Expo dev client keeps the menu key from its menu while a text field has focus (Back only hides the keyboard; the field keeps focus), and the error then says so: move focus out of the field, or tap Expo's floating `Tools` button (`tap --label Tools --element-type image`), then run `rn devmenu` again, which uses a menu that is already open. In `batch`, `rn devmenu reload` (an item or `--label` is required) is an input step, so `--step "rn devmenu reload" --step "wait --id <id> --timeout 20"` reloads and waits in one command. `rn tools off` turns off the element inspector and the performance monitor when they show, before screenshots; on Android the performance monitor shows only once the app may draw over other apps, so `rn devmenu perf-monitor` exits 1 `person_required` with nothing sent until the user turns on Display over other apps for it. A physical iPhone or iPad refuses `shake` and two-finger touches, so Offsider cannot open the menu there: ask the user to shake the device (or open the menu from the app), then run `rn devmenu`, which uses a menu that is already open. It counts a screen as the menu only when `Reload` sits beside two other menu items (or under React Native's title), so an app's own Reload button is never taken for it.
- `offsider shake` opens the dev menu on iOS simulator debug builds (`Reload`, `Go home`; close with `tap --id xmark`); release builds ignore it. Android has no shake: use `rn devmenu`, or `button menu`. Never try a Meta key combination for it, which a phone maps to a system shortcut. Taps on elements under the open dev menu get no cover warning, so close it first.
- An app dev menu behind a two-finger hold (a feature flag or debug panel) opens with `touch -x <X> -y <Y> --fingers 2 --hold 1000` on a simulator, an Android emulator or an Android phone (the phone's two fingers go through the UiAutomation helper); a physical iPhone or iPad refuses it.
