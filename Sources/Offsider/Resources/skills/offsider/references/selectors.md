# Selectors, coordinates and gestures

## Selectors

- Prefer selectors (`tap --id`, `tap --label`, `slider --id`, `slider --label`) over raw coordinates: they are resilient to layout changes, work across device sizes and wait for elements with `--wait-timeout`.
- `--id`, `--label` and `--value` match a node's `id`, `label` and `value` from `describe-ui`. In React Native apps, `testID` appears as `id`.
- `--element-type` narrows matches by `role` in any case (`button`, `switch`, `slider`) or by the exact native type (`RadioButton`, `TextEditor`).
- On `tap`, `wait` and `assert`, `--id` with `--label` (or `--label-contains`), `--value` or both matches only an element that has all of them, such as `tap --id size-btn --label M` among buttons sharing one id. When the id matches but no match has that label or value, it fails as not found and lists them. `wait --any` still takes each selector on its own.
- Copy `--label` and `--value` text from `describe-ui`. Typographic quotes and odd spaces fold to their plain forms when nothing matches exactly (`--label "Don't Allow"` finds `Don’t Allow`), and a miss suggests the closest labels ("Did you mean ...?"), saying which start with or hold your text; each candidate's `closeness` is `case`, `prefix`, `contains` or `similar`.
- `--label-contains <text>` matches a label that holds the text anywhere, in the same case, for a label React Native merged from a heading and its detail (`--label-contains 'Choose a layout'` finds `Choose a layout. Rows can show as a list or a grid, and the grid holds up to four columns.`). It works on `tap`, `slider`, `wait` (repeatable with `--any`), `assert`, `type --into-label-contains` and `screenshot --mask-label-contains`, can narrow an `--id`, and is refused beside `--label`; several matches are ambiguous as with `--label`.
- On screen means a touch at the element's point reaches it: its frame meets the screen, no page is drawn over its screen, and the simulator's hit-test or Android's drawing order finds it there (a physical iPhone has only pages). `wait`, `assert`, `tap`, `--verify-id` and `describe-ui --on-screen` share this, so a closed side menu kept mounted under the page, or a row under a tab bar, is not on screen: `wait` reports `under button "…"` or `beneath "…"`, `--summary` folds it into `# covered: N elements under others: id=…`, and `--allow-offscreen` still finds it.
- Selectors prefer matches that are on screen. Apps often keep views mounted off screen (a closed bottom sheet parked below the screen, rows below the fold), so a match whose frame is outside the screen fails with an "is off screen" error naming its frame instead of tapping nothing. Scroll it into view or open the sheet first; `--wait-timeout` waits for it to come on screen. A match inside the screen but above or below what its scroll view or list shows (a row below the fold, under a footer pinned beneath the list) fails the same way, with "below the fold of its scroll view; scroll first"; a row partly showing is tapped in the middle of the part its scroll view shows. `--allow-offscreen` on `tap` and `slider` resolves it anyway.
- With several matches, a selector takes the only one not on a screen beneath a full-screen page (a pushed page drawn over a screen that stays mounted); on Android, else the only one whose point Android's drawing order leaves uncovered, the one the tap's own cover check would let through (a pushed page's full-width button drawn over a half-width one with the same label); and when the matches share one point, such as two stacked Back buttons, it taps that point, which reaches the one on top. Matches side by side, each reaching its own point, stay ambiguous.
- When `tap --label` still reports multiple matches (exit 6), pick from the `candidates`, prefer `--id`, narrow with `--element-type`, or fall back to `tap -x <X> -y <Y>`. Each candidate names its `index` (the number `--nth` takes), its `window`, its `screen` (the page or covered screen it is on, else the id of the screen-filling view it sits in) and `beneath` (true when a page covers it). `tap --nth <n>` taps the nth on-screen match in tree order; `tap --topmost` taps the one drawn on top (the only one on the front page when a page is drawn over the others, else the one a hit-test reaches on an iOS simulator, by Android's drawing order on Android, else the last in tree order), for a screen whose earlier pages stay mounted with the same ids.
- For UIKit `UISwitch` and SwiftUI `Toggle` rows, selector taps activate the contained switch or toggle when the match contains exactly one such control. The default `--tap-style automatic` uses physical touch down and up for switches and toggles and a single tap event for other taps; `--tap-style physical|simulator` forces one.
- Selector `tap` and `slider` wait out up to 500 ms after a recent input and tap the target where it settled; `--no-settle` skips that. An animation longer than 500 ms still needs `wait --settled` first.
- A selector `tap` refuses (`target_covered`, exit 1, nothing sent) when a hit-test on an iOS simulator, or Android's drawing order, finds another element over its target, such as a pushed page's button over a tab of the screen beneath, or when its point falls in a React Native LogBox toast's touch area (from a point above the toast's top edge, plus the status bar's height on an edge-to-edge Android app, to the bottom of the screen); the message and `coveredBy` name it. `--wait-timeout` reads again until the cover goes; `--allow-covered` taps anyway. On an iOS simulator a prompt another process draws, such as Save Password? after a sign-in, refuses too (`evidence` `otherProcess`): a tap there would only dismiss it, so answer it from a screenshot or tap its backdrop as the message says, then retry. On a simulator a target partly showing beside its cover (a row half under a tab bar) is tapped on the part that shows once a hit-test there finds it. Where only tree order suggests a cover (a physical iPhone or iPad, Android without drawing order, a hit-test that answered with the screen's root, or an iOS hit-test that answered with a row while a control outside its scroll view, such as a floating footer, holds the point) it warns on stderr and taps; `--fail-if-covered` refuses then too. On Android an unlabelled full-screen React Native view drawn over the target warns too, since React takes its touches, unless it sits on the target's own page, where Offsider judges what lies beneath it; a native host off every page, such as an Expo dev client's tools button, does not. System scroll indicators (sliders such as "Vertical scroll bar, 3 pages") take no taps and are never a cover, nor are an identical twin on the page beneath, anything holding the target, or anything but a key over a key of a keypad the app draws. Overlays hidden from accessibility give no warning: when the tree looks right and taps do nothing, take a `screenshot`. A target under the on-screen keyboard is always refused, by `tap` and `type --into-id` alike (`target_under_keyboard`, nothing sent): hide the keyboard (on Android, `button back`) or scroll the target above it, then retry. When only a keyboard toolbar shows (Gboard with a hardware keyboard), Back would go to the app, so the advice names a scroll instead.

## Coordinates and gestures

- Coordinate `tap`, `swipe`, `drag` and `touch` accept coordinates from `describe-ui` directly, in points (dp on Android). Offsider detects rotated landscape simulator orientation and letterboxed landscape-only app layouts automatically. A coordinate `tap` outside the screen prints a warning.
- `gesture` scroll presets are named for the finger: `scroll-up` swipes up and reveals content below, `scroll-down` reveals content above. Presets are sized to the foreground app's frame and go through the same orientation handling, so they fit any device and landscape; `--screen-width` and `--screen-height` override that size, in points (dp on Android) as the screen is currently oriented. `swipe-from-top-edge` opens Notification Centre (Android's notification shade) and `swipe-from-top-right-edge` opens Control Centre; edge swipes from the top or bottom start 2 points inside the screen. On an iOS simulator a swipe up from the bottom edge reaches the app, so use `button home` or `button app-switch`.
- Something that drags only after a long press (a reorderable row, a tile) needs a hold before the move: `drag ... --hold-ms 800`, or `gesture long-press-drag --x <X> --y <Y> --to-x <X2> --to-y <Y2>`. A plain `drag` holds 50 ms, so it scrolls or does nothing there. `--hold-end <ms>` on `drag` and `swipe` holds still before the lift, so a list stops without a fling. `--screenshot-at <ms>` on either captures the screen while the finger rests there (`guide screenshots`). On Android a held finger is reported where it rests every 50 ms, as a real one is, so a press-and-scrub chart sees the hold.
- Use `--pre-delay` and `--post-delay` on `tap`, `swipe` and `gesture` for fixed delays around actions, and `--duration` for how long a swipe, gesture, button press or key press lasts.
- Keep a held touch in one command (`touch --down --up`) or one `batch`.
- `gesture pinch --from 60 --to 240 --device <DEVICE_ID>` spreads two fingers about the app frame's middle (or `--x`, `--y`) to zoom in; `--from 240 --to 60` squeezes to zoom out (spreads 20 to 600, `--duration` default 0.5 s). Same devices as two-finger `touch`; check the zoom with a screenshot.
- `touch -x <X> -y <Y> --fingers 2 --hold <ms>` puts two fingers down `--spread` points apart (default 60) around the point, holds them and lifts both, for menus behind a two-finger hold. It works on a simulator's main display, Android emulators (gRPC) and Android phones (the UiAutomation helper, started for the command, about 1.7 s on a Pixel); `OFFSIDER_ANDROID_INPUT=input`, a physical iPhone and the iPhone Duo's inner display refuse it.

```bash
offsider tap --label 'Weather Alerts' --device <DEVICE_ID>
offsider tap -x <X> -y <Y> --tap-style physical --device <DEVICE_ID>
offsider drag --start-x <X1> --start-y <Y1> --end-x <X2> --end-y <Y2> --device <DEVICE_ID>
offsider gesture scroll-up --device <DEVICE_ID>
offsider slider --label <text> --value 40 --element-type slider --device <DEVICE_ID>
```

## Text and buttons

- `type` adds to the focused field. Tap the field, then `type --replace 'text'` sets it exactly and `--replace ''` clears it; it works with `--stdin`, `--file`, `--verify` and as a batch step. iOS selects all with Command-A and deletes, then types (secure fields included); Android sets the text in one step.
- With no `--into-id`, `--into-label`, `--into-label-contains` or `--require-focus-id`, `type` sends nothing unless a text field has focus (or an iOS simulator shows a keyboard): exit 1 `no_focused_field`, since keys that reach no field act as app shortcuts (a React Native dev build reloads on `r`). Focus on an app's own keypad button, or on Android a keyboard up for a field hidden from the tree, refuses too: tap the keypad's keys instead. `key-sequence` with letters, digits or punctuation follows the same rule. On an iOS simulator keys into a React Native app go 30 ms apart, so a field that sets its text on each change keeps them in order.
- `type --into-id <id>` (or `--into-label`, `--into-label-contains`) taps the field and waits up to 2 s for it to take focus before typing; when it never does, nothing is typed and it exits 5 (`focus_not_confirmed`). An iOS simulator reports the field's own focus, so a connected hardware keyboard, which hides the software one, does not stop it; only where the simulator names no focused element does a keyboard appearing count, and a keyboard already up then types with a `Warning:`, so check the field with `assert --has-value`. `type --require-focus-id <id>` types only when that field already has focus and exits 2 (`focus_mismatch`, naming the focused field) otherwise. Text the simulator keyboard cannot type fails before the focus tap.
- A trailing newline presses Return on both platforms, so `$'query\n'` submits. Use single quotes inline, and `--stdin` or `--file` for shell-sensitive text.
- While a recording runs, `type --stdin` or `--file` exits 8 `device_busy` with a password field on screen, typing nothing; stop the recording first.
- Text given as an argument into a password field (by `--into-id`, `--into-label`, `--require-focus-id`, or the focused field) exits 64 `secure_field_argument` with nothing typed: sign in with `login`, or pass the secret with `--stdin`.
- `--file` reads a regular UTF-8 file of at most 64 KiB and says on stderr which file it read. Files under `~/.ssh`, `~/.aws`, `~/.config` and similar, and names such as `.env` or `id_rsa`, exit 64 `input_file_refused`; `--allow-path` reads one only after the user confirms it with Touch ID or the password at a terminal (`person_required` for you), so ask them.
- `button` names depend on the device: an iOS simulator has `apple-pay`, `app-switch` (Home twice), `home`, `lock`, `side-button` and `siri`; a physical iPhone or iPad has `home`, `lock`, `side-button` and `siri`; Android has `back`, `app-switch`, `home`, `lock` (the power key), `menu`, `volume-up` and `volume-down`. A button the device lacks exits 64.

## Sliders

- Use `offsider slider --id <identifier> --value <0-100>` instead of approximating with raw swipe coordinates. It always checks its own result: it re-reads the slider's `value` and fails clearly if the observed 0 to 100 value stays outside tolerance.
- On iOS it sends one calibrated low-level HID drag from the resolved slider frame and current `value`, through the same composite touch-move path as `drag`. iOS slider controls quantise values to their rendered track resolution, so Offsider does not retry correction gestures to chase unreachable decimals.
- On Android it uses the accessibility progress action (`guide android`).
